# Platform capabilities and verification scope

Updated: 2026-10-29. The tables below are compiled from [bern-target-api](../../crates/bern-target-api/src/lib.rs) and each backend's `TargetDescriptor.features`. macOS and iOS share one SwiftUI list; tvOS shares the SwiftUI generator with them, and its list is given separately in the [tvOS descriptor](../../crates/bern-backend-swiftui/src/tvos.rs).

The optional GPUI target (`ui = "gpui"`, macOS, Windows, Linux) is a first version, built and run on all three platforms, and is not included in the tables below; the components and features it declares are in the [GPUI implementation notes](../Implementation/GPUI.md).

## Compile-time feature support

"Supported" means the backend declares that it accepts the corresponding feature; "Not applicable" means the backend also declares that it accepts it, but there is no corresponding behavior there (for example, TVs and desktop windows have no orientation to rotate), and using it reports neither an error nor a warning; "—" means not declared, and declarations that use the feature are rejected by the corresponding capability check. It does not mean that every property behavior, visual effect or device scenario has passed acceptance. Color overrides, motion, windows and media also have separate capability descriptions; full support cannot be inferred from this table alone.

## Capabilities not fully expressed by the feature flags above

| Capability | Current scope |
| --- | --- |
| `Window(idle_enabled:)` | All six targets consume the on/off state (capability `idle_control`): when it is false, `window.idle` stays false and no time is counted; when it becomes true, timing restarts |
| Idle area (`idle_area`) | The motion capabilities of all seven targets declare it. On macOS, Web, Android, Linux and Windows, when the page has an idle area, the window goes idle only when the mouse rests over the idle area; resting elsewhere or leaving the window keeps it awake, and touch, remote and keyboard still follow `idle_after`; on iOS and tvOS the idle area does not change the timing (also on an iPad with a mouse attached). macOS measured with the playback screen of a real app; Web has runtime tests; Android compiles and packages, both Windows frontends compile with MSVC, and the Linux runtime passes Clippy on GTK 4 on macOS, but none of these three has been run and measured |
| `Window(landscape:)` on the web | Locks to landscape through the Screen Orientation API: browsers lock only on phones and tablets, most also require the page to be full screen or running as an installed app, and Safari on iOS does not offer locking; when refused, the device orientation is kept and the request is made again on entering full screen. Covered by runtime tests, not measured in a phone browser |
| Image Hero across split columns | macOS uses a window-level overlay, Web uses a viewport-level copy; iOS and other macOS views keep using matched geometry. Continuous-frame handoff for Video is verified separately |
| Local persistence | The native FFI host provides file storage, and the Web app uses same-origin localStorage; nothing is persisted when no storage host is installed |
| Optional Svg | Six targets have a generation path; tvOS has no WebKit, so it is unavailable there and the check reports an error when it is used; for its dedicated dependencies and verification see [Animated SVG](../Implementation/Animated-SVG.md); it does not change the default implementation of ordinary UI |
| Per-platform app icons (`[app.icon]`) | All seven targets accept a square PNG and their own native format: macOS `.icns`, iOS `.appiconset` (both also accept Icon Composer's `.icon`, the Liquid Glass icon from 26 on), tvOS `.brandassets` (when not declared, the layered icons and the top shelf image are generated from the default icon), Windows `.ico`, Linux hicolor icon theme, Android `res`, Web page icon folder or SVG; checked at the configuration stage and used as is during generation. Rules in [App icon](../Design.md#app-icon) |
| `SidebarHeader(role: title)` | Not shown on WinUI 3 and system XAML (the title bar already shows the app icon and title); not shown on GTK (the sidebar's title bar already shows the app name, and KDE, following its button layout, also shows the app icon at the leading edge); other targets show it as usual |
| TV layout (`Layout(size: tv)`, `window.tv`) | tvOS is always a TV: at build time only the `tv` layout is kept and pruned by the known window conditions (measured). Android decides by the system's TV mode or the leanback feature, and Web by the user agent of TV browsers; not verified on TV devices. On macOS, iOS, Windows and Linux it is always false, and the `tv` layout is not generated |
| `Shortcut` | Shortcuts without a control, generated on six targets: keyboard shortcuts on macOS, iOS, Web, Android, Linux and Windows; remote buttons on tvOS and Android TV (`escape` is back, `space` is play/pause, arrow keys are directions when focus has nowhere to move). A disabled shortcut yields its key to the one shown before it (covered by Web runtime tests). Arrow keys measured on the tvOS simulator; back and play/pause, Android TV, and the keys on other targets not measured |
| TV font size (`font(tv:)` in a `text` block) | tvOS takes the TV font size at build time (measured on the simulator); Android and Web take it when the runtime decides it is a TV (Web switches through the `bern-television` class; not verified on TV devices); macOS, iOS, Windows and Linux are unaffected. Covered by each backend's generator tests |
| Text session actions (`push_str`, `pop`) | Generated on six targets; input and deletion measured through the on-screen keyboard on the tvOS simulator; SwiftUI type-checked for tvOS and macOS, Compose compiled with the Android build, GTK compiled on the Ubuntu VM, WinUI 3 compiled on the Windows PC |
| `Search(suggest: true)` | Lists results before anything is typed: SwiftUI and Web when focused, and on TV at all times (measured on the tvOS simulator); Compose's toolbar search page lists them on opening anyway; GTK and WinUI 3 pop them up when focused. Interaction not measured outside tvOS |
| Performance tracing (`BERN_TRACE`, `trace.*`, `bern run --trace`) | The shared Rust side is the same for all targets: rules and filters, recording and aggregation, the timeline, session commands, and the spans of the engine (queueing, execution, snapshots, comparison, module calls, `span!`) and the bridge (decoding, per-field encoding, callback triggering). Instrumentation on each frontend's UI thread is not yet hooked up, so interaction chains and long frames do not appear yet. See [Performance tracing](Tracing.md) |
| `default_focus` | `Button` / `IconButton` takes focus when it appears, generated on six targets: on tvOS it is the preferred focus of the focus section (measured on the simulator), macOS / iOS use `FocusState`, Web calls `focus()`, Compose uses `FocusRequester`, and GTK and WinUI 3 request focus after the control is shown; not measured outside tvOS; GTK compiled on an Ubuntu 24.04 VM and passed Clippy and the type check of the generated app, and WinUI 3 compiled the generated gallery with MSVC on the Windows PC |
