# Linux GTK implementation notes

For the current component interfaces see the [component reference](../Reference/UI.md); for per-item support and the scope of recent verification see the [platform capability table](../Reference/Platforms.md). The sections below keep the implementation and acceptance records of each phase.

- Date: 2026-10-11 (the v0.29 and v0.30 capabilities were filled in on 2026-10-14, see "Style, motion, self-drawing and media-app capabilities"; the page-level layout, scene and control-shape capabilities were filled in on 2026-10-18, see the section of the same name)
- Basis: [Bern architecture design v0.30](../Design.md) (originally implemented against v0.15), [Windows and Linux adaptation](../Adaptation/WindowsLinux.md)
- Toolchain: Rust 1.99.0; gtk4-rs 0.11 (`gtk4`, with `v4_14` enabled), libadwaita-rs 0.9 (with `v1_5` enabled), glib/gio 0.22
- Verification environment: Ubuntu 24.04 LTS (aarch64, VMware Fusion virtual machine), GNOME Shell 46.0, Wayland session; GTK 4.14.5, libadwaita 1.5.0, GStreamer 1.24.2

This document records what was actually completed for the `gtk + linux` target in Phase 5. The declaration, protocol, business core and IR of the same showcase app (`examples/showcase`) are unchanged; only `[targets.linux]` was added, and the new GTK target module generates the Linux app; the parser, the shared IR, the core check rules and the business core were not modified in any way for GTK. The general acceptance of Phase 2 and Phase 4 was rerun on Linux; the results are in "Verification log". WinUI 3 and `flutter + macos` belong to later batches of Phase 5 and were not started in this round.

## Project structure

| crate | Responsibility |
| --- | --- |
| `bern-backend-gtk` | The `gtk + linux` target: description, checks, generating Rust source from the IR, generating the app crate and the build plan. A workspace member; does not depend on GTK |
| `bern-gtk` | GTK 4 runtime: reactive cells, controls, windows, session commands, queries and the media executor. Not a workspace member (`exclude`); compiled only in the generated app |
| Generated app crate | `target/bern/linux/app/`: `ui.rs` (components, windows, string tables and `AppDef`), `main.rs` (starts the engine), `cli.rs`, `mcp.rs` |

The generated code does not write a UI runtime of its own; it calls the standard components of `bern-gtk`, in the same form as the Web target: each component generates one function, expressions generate Rust expressions evaluated in the context `c`, local variables (component parameters, row variables, pattern bindings) live in the context, closures capture nothing, and bindings are re-evaluated only when a cell they read changes. Values are represented as the protocol's `Value`, and encoding and decoding use `bern-protocol` directly.

The engine, the session runtime and the UI are in the same process, connected through the same in-process interface (`bern-ffi`) as the SwiftUI and Web targets: the GTK runtime calls these functions directly, values are passed in the Bern binary layout, and callbacks arriving from the engine and channel threads copy their bytes and are handled on the GTK main thread in arrival order. The callback boundary catches panics; an error in one callback is only logged and does not terminate the app.

## Control mapping

Based on the GNOME HIG and the standard controls of libadwaita 1.5; controls in forms are all libadwaita rows, placed in lists with the `boxed-list` style.

| Bern | GTK / libadwaita |
| --- | --- |
| `Window` | `AdwApplicationWindow` whose content is an `AdwToolbarView` with an `AdwHeaderBar`; a `ToastOverlay` shows failed commands |
| `SplitView` / `Sidebar` / `Detail` | `AdwNavigationSplitView`; the sidebar is a list with the `navigation-sidebar` style, section headers and a search field; the detail page's header bar shows the selected destination, tools and back; collapses to a single column when the window is narrower than 400sp |
| `Navigation` / `Destination` / `NavLink` | The root content and top-level destinations sit in a `GtkStack` and slide left and right; the root content stays mounted while a destination is pushed; the back button, Esc and Alt+← go back; in forms a link is an activatable row ending with a `go-next` icon |
| `Tabs` / `Tab` | `AdwViewStack` with an `AdwViewSwitcher` in the header bar; only the selected tab is built |
| `Toolbar` | The end of its page's header bar; the root page's tools are hidden when a destination is pushed |
| `Form` / `Section` | A scrolling page with `AdwClamp` (680); a section is a title, a `boxed-list` list and a footer |
| `Text` / `Label` | `GtkLabel` with libadwaita typography classes (`title-1`…`title-4`, `heading`, `caption`, `dim-label`); a `Label` in a form is an `AdwActionRow` with a prefix icon |
| `Button` / `IconButton` | `GtkButton`; `prominent` is `suggested-action`, `plain` is `flat`, `destructive` is `destructive-action`; icon buttons have no border, and their name is the tooltip and the accessible name |
| `TextInput` | In forms, `AdwEntryRow` or `AdwPasswordEntryRow`; multi-line is a bordered `GtkTextView`, with `prompt` as a line of `dim-label` laid over the empty input (`GtkTextView` has no placeholder text; the prompt does not receive clicks and hides once there is text); elsewhere `GtkEntry` |
| `Search` | `GtkSearchEntry`; Esc clears it |
| `Switch` | `AdwSwitchRow` in forms; the `checkbox` style is a row with a `GtkCheckButton` |
| `Slider` | Within a row, a title and a `GtkScale` with icons at both ends; dragging only changes this window's preview and commits once on release, while keyboard and scroll wheel commit immediately |
| `Picker` | `segmented` is a `linked` group of toggle buttons; `chips` are unlinked `GtkToggleButton`s in one group (`set_group`): inside a `Flow` with no label shown, each button is a child of the Flow, otherwise they go into their own `BernFlow` (spacing 8); everything else is an `AdwComboRow` or a `GtkDropDown` |
| `Menu` / `MenuItem` | `GtkMenuButton` with a `GMenu`; menu items are actions whose availability comes from the declaration |
| `LanguagePicker` | `AdwComboRow` whose options are each language's name for itself |
| `Query` | Loading: spinner and text; empty result and failure without data: a compact `AdwStatusPage` (failure has "Retry"); refreshing and failure with data: a status line above the data |
| `Adaptive` / `Layout` | A zero-height drawing area measures the available width and picks the layout by the `[layouts]` breakpoints |
| `Video` | A `GtkPicture` shows the player's `GtkMediaFile`, with the standard control bar below it (see "Media") |
| `Image` | A `GtkPicture` (`content-fit` corresponds to `fit`, can shrink) inside a fixed-size `BernPictureFrame`: `GtkPicture` itself requests the original image size, and this widget limits it to the declared width and height and keeps it at the leading edge when it gets more space; when only one side is given, the other follows the image's aspect ratio. JPEG is decoded through gdk-pixbuf and turned upright by its EXIF orientation (GTK 4.14's own loader ignores orientation); other formats use GTK's loader. The pixels read by gdk-pixbuf are converted to premultiplied RGBA8 before being made into a texture: a texture made directly from the pixbuf is three-byte RGB, which the renderer converts pixel by pixel through floating point on the UI thread when uploading (GTK 4.24's `r8g8b8_to_float` and `r8g8b8x8_from_float`), and on the Steam Deck switching to a page with more than a hundred posters froze one frame for about half a second. Images in state (`RuntimeImage`, posters and so on) are decoded on a background thread (`gio::spawn_blocking`); when the width and height are fixed they are decoded at frame points × the largest display scale × 2 (2× supersampling, only downscaled, never upscaled, JPEG already downscaled while decoding), and recently used textures are cached by address and decoded size (up to about 96 MB), so showing the same image again does not read, decode or upload it again. Measured (2026-10-27, Steam Deck, release): switching to the page with more than a hundred posters, the longest frame dropped from 499–569 ms to 66 ms (about 34 ms when entering again), and dropped frames went from over fifty per switch to one to three; switching between the home page and the media library no longer has frames over 25 ms. HDR images (PQ and HLG PNGs, JPEGs with a gain map) are decoded by `bern-image`: from GTK 4.16, on Wayland with color management turned on (on by default from 4.16 to 4.18.0; from 4.18.1 the user has to set `GDK_DEBUG=color-mgmt`), they are handed to GTK with the full gain in linear BT.2020 (`GdkMemoryTextureBuilder` and rec2100-linear, looked up at runtime, so the same program also runs on 4.14); in other cases they are first converted to SDR: gain-map images use the SDR image the author provided, and PQ and HLG are tone-mapped. Measured on GTK 4.14: PQ images no longer look washed out, and gain-map images show the SDR image. `label` is the alt text; without it the image is hidden from assistive technologies |
| `Progress` | With `value`, a `GtkProgressBar` under the label, named by the label; without it, a `GtkSpinner` with `dim-label` text (libadwaita 1.5 does not have `AdwSpinner` yet) |
| `Grid` | A `GtkFlowBox` of equal-width cells: each cell is at least `min_width` wide, not selectable, and the cells themselves do not take focus; a bound `min_width` changes along the `animate` spring, and the column count changes with it |
| `Stack` | `BernLayers`: children are stacked in the same place, later ones on top and receiving input first, aligned by `align`; the whole is as large as the largest layer and stays at the leading edge when it gets more space, unless some layer wants to fill (a canvas, rail or video without a size, and so on; GTK's expand propagates upward) |
| `Canvas` | `BernCanvas` (see "Self-drawing"); in a direction without `width` or `height` it fills the available space; with `label` it is a named image, without it it is hidden from assistive technologies |
| `Text(mark:)` | `BernMarkedText`: under the label, draws a capsule-shaped highlight along the logical extent of each Pango line (74% to 98% of the line height, extending 0.4 character widths past the right end), redrawn when the text or the theme changes |
| `Rail` | `BernRail`: along the axis it takes the length it is given, and across the axis it is as thick as its thickest child; `at` children align their `anchor` to the fraction point, `from`/`to` children span the space between the two points and fill the thickness when they have no cross size; changes of the fractions move along the `animate` spring. The rail asks for outside space only along the axis: children without a size do not make the outer container grow in the cross direction. In a `Stack` the rail spans the length the other layers give along the axis, and in the cross direction it counts only its sized children: when it has only such children, the rail stands at the stack's alignment position with their thickness (a progress bar at the bottom of the picture); when some child has no size of its own in the cross direction, it fills the whole layer. Whether a child "has a size" depends on whether it wants to expand in the cross direction, not on its measured size: a card button with only a stroke behind its column measures as the stroke's 2 pixels, and previously the whole rail was therefore only 2 pixels high and stuck to the top of the column |
| `SidebarFooter` | A bar below the sidebar list, under a separator; the list scrolls above it |
| `Inspector` | The trailing sidebar of an `AdwOverlaySplitView`: `presented` is bound both ways; in wide windows it pushes the content aside, and when narrower than 640sp it floats over the content |
| `Toast` | An `AdwToast` in the window's `AdwToastOverlay`, replaced when `key` or the content changes, dismissed after `duration` seconds; with `icon` the title is an icon plus text |
| `SplitButton` | A `linked` toggle button plus an arrow menu button, with the children in the popover (always mounted) |
| `PopoverButton` | `GtkMenuButton` with a `GtkPopover`: children are mounted while the popover is shown and unmounted when it closes; `presented` is bound both ways. When it is opened by state or by the session's `activate`, popovers open elsewhere in the same window are closed first (the popover it sits inside is kept), the same as clicking once outside a popover: on Wayland a grabbing popup can only open on top of the topmost popup, and when it opens next to another popover GDK refuses to map it ("Tried to map a grabbing popup with a non-top most parent") while GTK treats it as open, and it then swallows all later clicks and taps. This is what happened before when "More danmaku settings…" in the danmaku popover of the player screen opened the playback settings: the settings did not appear, the danmaku popover could not be closed, and after closing it with Esc every button only showed its pressed look and did nothing (2026-10-27, KDE Wayland on the Steam Deck) |
| `Drop` | `GtkDropTarget` (file list, with the value preloaded so it can reject by kind): `over` is true while acceptable files pass over it, and on release they are stored in the field and the action runs; with `opens: true` the app receives files handed over by the system (`GApplication`'s open), and the desktop file registers `MimeType` and `%U` |
| `Pinch` / `Swipe` | `GtkGestureZoom` (also accepts Ctrl plus scroll wheel) / `GtkGestureDrag` (starts after 10 points, `distance` defaults to 300) |
| `Switch(style: button)`, `Switch` in a toolbar | `GtkToggleButton`; in a toolbar, only the icon is shown when there is one |
| `Button` with content | A frameless `GtkButton` showing its content as is; `overflow: hidden` lets the style's corner radius clip the content; without a style it darkens when pressed. With `shape: capsule` it is the platform button wrapping the content, and the content is centered both horizontally and vertically in the button, as with a label (previously a capsule with a declared height was taller than its content, and the content stuck to the top edge) |
| `Search` in a toolbar | A `GtkSearchEntry` at the end of the header bar; its children are in a `GtkPopover` that does not take focus, shown while the entry has focus and text, and dismissed after a result is picked |

Icons use Bern's SF Symbols names, mapped to freedesktop symbolic icon names (for example `magnifyingglass` → `system-search-symbolic`) and drawn by Adwaita: at startup, as long as Adwaita is installed, the app's `gtk-icon-theme-name` is set to Adwaita (the display's own icon theme does not accept being renamed directly), and the desktop's icon theme is not followed; KDE's Breeze lacks many of the names in the table and draws others in color (seen on KDE on the Steam Deck, 2026-10-27). There is only one mapping table (`crates/bern-gtk/src/icon_table.rs`, sorted by name): the runtime reads it, and `bern-backend-gtk` also reads it with `include!`; when an app uses a name that is not in the table, the check reports an error pointing at the declaration, instead of a missing icon showing at runtime. All icons in the table are in Adwaita 46 (themes such as Yaru eventually fall back to Adwaita through `Inherits`); only `arrow.up.right.square` uses `adw-external-link-symbolic` from libadwaita's bundled resources. The table contains at least all names of the Bern icon set (`bern_target_api::icon_set::NAMES`).

## Runtime structure

- **Windows and drafts**: when a window appears it registers with the session runtime and gets a generation and an external ID (`main#1`), and its draft cells are created from the initial values the runtime returns; writes go through the runtime first and then update the cells. Closing a window releases its drafts, control registrations and query subscriptions; app-level players keep going.
- **Control registration and session commands**: when mounted, actionable controls register a target ID (`component.control_id`, with `[key]` appended for list rows), role, name, availability and action closure, and external `ui.*` commands run through these closures; disabled, blocked by a close confirmation and mounted in several places return `target_unavailable`, `target_blocked` and `target_ambiguous` respectively; password fields do not expose their values.
- **App lifecycle**: `AdwApplication` uses `bundle_id` as the application ID, and only one instance runs per user; after the last window closes the app keeps running (the engine and external entry points stay available), and launching the app again opens the main window; when a `StatusItem` is declared it sits in the desktop's status area, from where windows can be opened or the app quit (see "Status bar item"). Ctrl+Q quits (like Cmd-Q on macOS, without going through the close checks), Ctrl+W closes the current window, and Esc closes the settings window.
- **External entry points**: the same local control channel as on macOS (`channels = ["ipc"]`); the CLI and the MCP server are generated from the same command catalog.

## Windows

- **Close protocol**: the header bar's close button, Ctrl+W, declared actions and `window.close` all evaluate the close check first. When confirmation is needed it is shown as an `AdwAlertDialog` with the buttons "Save / Don't Save / Cancel" or "Discard Changes / Cancel"; while it is pending the window's content cannot be operated, and external entry points return `target_blocked`. Once closing is decided the window is destroyed directly: while the dialog is still in its closing animation, another close request would only close the dialog.
- **Facts**: visibility, size state (normal, maximized, fullscreen), window size, whether it is focused, and the available actions are reported to the session runtime as facts with their source; when a value does not change, the version number does not change.
- **GTK 4 and Wayland limitations**:
  - GTK 4 has no interface for reading or setting the window position; `frame`'s `x` and `y` are always 0, and `window.move` is unavailable (`target_unavailable`).
  - GNOME's Wayland compositor does not report that a window is minimized (after minimizing it only loses focus, with no state flag). `window.minimize` sends the request as usual and then immediately answers with `ui_timeout`, stating that the result is unknown, instead of treating the request as completed; under X11 the minimized state is reported, and the command answers once the fact arrives. `window.activate` can bring the window back.
  - GNOME has focus-stealing prevention: an activation initiated by a background process does not necessarily get focus, and the facts reflect this as it is.
  - `window.maximize`, `window.restore` (leaving maximized or fullscreen) and `window.resize` answer only after the window has actually changed, and the result is the actual state recorded by the runtime; a size smaller than the declared minimum size returns `out_of_range`.

## Media

- The executor keeps one `GtkMediaFile` per `player_id` (GTK's media backend, GStreamer on Linux) and switches to a new media stream for each new source (the same stream keeps the first file's duration after its file is switched), carrying over volume and mute, and the picture showing it switches along; it reports readiness, playing, end, errors, duration, volume, mute, seeking and the position every 0.5 seconds to the media center as observations, and never dispatches commands. The build manifest records the media backend `gtk-mediafile` and the presentation `gtkpicture`.
- The player of `Video(source:)` belongs to the component instance; when the binding changes it loads by the new source version, and the same value is not loaded again; `Video(player:)` only attaches a presentation. The control bar (play/pause, progress, duration, mute, volume) only sends standard media commands, and its state comes from the media center; dragging progress and volume only updates the preview and commits once on release. The controls are registered as `target.play_pause`, `.position`, `.mute`, `.volume`.
- The position is reported every 0.5 seconds, and immediately when it jumps (for example when a seek completes); at the end the position equals the duration. The picture area keeps 16:9 at the available width.
- Errors show only the first sentence of the GStreamer message (without the element path); the full content is written to the log.
- **The app's own media core** (2026-10-27): at startup `bern_media_kernel_attach` is first asked with `FrameSink`; when the core accepts, the `GtkMediaFile` executor is not attached, and `Video` uses `BernKernelVideo` (`kernel.rs`) instead: a control that reports no natural size and draws the latest frame to fill itself. Once mapped it registers a callback on the frame clock; the first time it has a size it registers a frame sink (`register_frame_sink`) and hands the core the registration number, the physical pixel size (allocated size × `GdkSurface::scale`, fractional scaling supported) and `fit`, calling `bern_media_surface_resize` when the size or the pixel ratio changes; each frame it calls `bern_media_surface_frame` with the frame clock's `frame_time` as the time, targeting the predicted presentation time plus one refresh period. The core hands frames to the sink on its own thread; the sink keeps only the latest one and asks the UI thread to show it, and the UI thread makes it into a `GdkMemoryTexture` (RGBA8), scaled linearly to fill the control. On unmap and destroy the frame callback is stopped first, then `bern_media_surface_detach` is called synchronously and the sink is unregistered; the last frame is kept until it is shown the next time. Corner radius, opacity and transitions act on this control as usual, and the control bar sits on top of it. For the measurements see the [design document](../Design.md#app-provided-media-cores).
- **System dependencies**: GStreamer's H.264 and AAC decoders are not in Ubuntu's default installation and need `gstreamer1.0-libav`; without it the clip reports `Failed` ("Your GStreamer installation is missing a plug-in."), and `media.play` returns `media_failed`. HLS live streams in MPEG-TS also need `gstreamer1.0-plugins-bad` (`tsdemux`). Media network requests follow environment variables such as `http_proxy`.

## Localization and themes

- The string tables (the text the app declares, the app name and the runtime's own text) are generated into the program; at startup a supported language is chosen by `LANGUAGE`, `LC_ALL`, `LC_MESSAGES`, `LANG` (`zh_CN` maps to `zh-Hans`), `ui.set_language` and `LanguagePicker` switch it at runtime, and all text bindings are recomputed in the same update. The runtime's own text is built in for zh-Hans, zh-Hant, en and ja.
- Text with parameters and the enum labels that show a variant's fields are written out by the [message format](../Reference/UI.md#text-content-and-formatting): the runtime reuses `bern_protocol::format` directly (the same parsing and formatting as the compiler), arguments are passed by type (text, numbers carrying their numeric value, `CalendarDate`, enum labels), and the plural category comes from the current language. Month and weekday names are generated with the string tables, and languages beyond the built-in ones use English. The generated type table carries the labels' keys and parameters, and the label text still comes from the string tables. On 2026-10-19, on bern-ubuntu (Broadway), a temporary project measured the `=0` branch, enum labels inside plural branches, dates, durations and labels with fields in Chinese and English, and confirmed that a real app's English UI has only data such as titles left in the original language.
- The build generates a freedesktop desktop file (with the name in each language), which can be installed into `~/.local/share/applications`.
- All colors come from libadwaita: light and dark mode follow the system, and without style overrides the generated code sets no colors. A declared brand color maps to libadwaita's accent color. The semantic roles of style overrides and canvases map to libadwaita's named colors (see "Style overrides").

## Style, motion, self-drawing and media-app capabilities (v0.29, v0.30)

Filled in on 2026-10-14: the GTK capability description now lists styles (`Button`, `IconButton`, `SidebarItem`), motion (`appear`, `disappear`, `reflow`, `hero`, `animate`, `scroll_scale`, `scroll_opacity`, `nudge`, `stagger`), `window_chrome`, `text_marks`, `dynamic_items`, all drawing components and media-app components, and all 18 items in `features`. `examples/planner` and `examples/gallery` check on GTK with no errors and no warnings (test).

### Style overrides

- Each style in use generates a `StyleDef` table entry; the runtime writes them into one application-priority style sheet: the class `bern-style-<name>` is the base appearance, and `bern-selected`, `bern-hover`, `bern-pressed`, `bern-focus`, `bern-disabled` are the states in that order; at equal priority the later rule wins, which is exactly the merge order "selected, hover, pressed, focus, disabled". Properties a style does not set are left to the theme, so a `Button { pressed: scale(…) }` that only sets a transform keeps the libadwaita button's look and feedback; a state that sets a background covers the theme's hover background. `none` removes that state's feedback, and `system` keeps the theme's. Color changes use a 150 ms CSS transition.
- States come from GTK's own state flags (`PRELIGHT`, `ACTIVE`, `FOCUS_VISIBLE`, `INSENSITIVE`, `SELECTED`/`CHECKED`), with no extra event controllers installed; keyboard presses and pointer presses are both `ACTIVE`.
- Scale, offset and opacity act on the `BernMotion` wrapping the control (see "Motion"), entering with the spring the state carries and returning to the normal state with `settle`; the target can change mid-animation.
- When a sidebar item has a style, the row itself no longer draws a background; the style is drawn on the row content, and the content scales with the state inside a `BernMotion`; states that are not set keep the look of the libadwaita sidebar (7% foreground color on hover, 10% when selected, 16% when pressed). Selection is driven by the row's `SELECTED` flag; the row is still a `GtkListBox` row, and keyboard navigation is unchanged (not measured).
- Size classes: `small` has a minimum height of 24, `large` 44, `extra_large` 52, with padding and font size adjusted; `corner` is `border-radius`, buttons with content also get `overflow: hidden` to clip the content, and `shadow` is a `box-shadow` following the corner radius; when a style draws no background, stroke or fill in any state (bare icons and text floating over a picture), the shadow is cast by the content instead: the motion box first pushes a GSK shadow node when drawing (`push_shadow`; radius, downward offset and opacity mean the same as in CSS, the same quantity as `drop-shadow` on the Web and `BlurRadius` on Windows), and the shadow has the shape of the glyphs and icons, not a box. `Stack`'s `shadow` works the same way: without a background, the stack casts the shadow of what its layers draw (text, icons, progress bars, canvases); with a background it is a `box-shadow`. Previously GTK did not support shadows on `Stack` and button shadows were only boxes, so the player screen had no shadows on Linux, and white controls and text could not be made out on an all-white picture (2026-10-27).
- Semantic roles map to libadwaita's named colors: `surface.canvas` → `window_bg_color`, `surface.panel` → `card_bg_color`, `surface.raised` → `popover_bg_color`, `text.primary` → `window_fg_color`, `text.secondary` → 55% of it, `accent` → `accent_bg_color`, `on_accent` → `accent_fg_color`, `status.*` → `success`/`warning`/`error_bg_color`, `fill.subtle` → 7% foreground color, `fill.strong`, `control.track`, `control.border` → 15%. A fixed `color(light:, dark:)` takes its value by the current appearance, and the style sheet is rewritten when the appearance changes.

### Motion

- Springs are libadwaita's `AdwSpringAnimation`: mass 1, stiffness (2π / T)², damping ratio ζ; when the target changes they continue from the current value and velocity. Animations are driven by the control's frame clock and jump straight to the end while the control is not on screen, so transitions such as appear start only once the element is on screen. When the system turns animations off (`gtk-enable-animations`) or with `BERN_MOTION=reduce`, state transforms, stagger, nudges and scroll-linked effects do not run, and appear and disappear only do a 0.15-second fade; when the system turns animations off, libadwaita also jumps this fade straight to the end.
- `BernMotion` has a single child control and measures the same as the child; on allocation it gives the child a transform with the child's center as the origin, so motion does not change layout; the transform is composed from the springs of several layers (style state, appear, disappear, shared element, nudge, scroll-linked, visibility): offsets add, scale and opacity multiply.
- Appear and disappear: elements mounted by `if`, `match` and `ForEach` after the first display play `appear`; elements inside such an element appear together with it and do not play their own, except that the children of stagger containers inside it still appear in their turns (see the next item). An unmounted element with `disappear` stays in its container until it has finished playing and then leaves; by then it is no longer in its own area, and new elements are inserted at the positions they would have if it were not there. List rows are laid out by the list: the row itself does not move, and the row's content moves within the row.
- `stagger`: a container builds its direct children with a counter, and children with `appear` are each delayed by a further `stagger` seconds; when the container appears in an update (itself, or together with the element it is in, at any depth, for example as a page enters), its children play their appear too; the rows of a `ForEach` are its children, counted from 0 in each update. A staggered `ForEach` builds only the first new row right away and builds each of the other rows only on the frame before its turn, at most one row per frame, driven by the frame clock of the rows already built; the positions of all rows are reserved from the start, the rows arrive in order, and they enter at the same moments as if they had all been built together. If a page of rows that enter one by one were built and laid out in the same frame (mostly measuring new text), that frame would stall; with Reduce Motion there is no stagger, and everything is built at once as usual.
- Shared element `hero`: when an element unmounts, its position in the window is recorded and a snapshot of it is kept (not for video and canvases, which change by themselves); after a new element with the same key in the same window is laid out, it expands from the old position and size with the `hero` spring, while the old snapshot moves along in a `GtkFixed` layer above the window and fades out.
- `reflow`: a `Column` or `Row` that sets it, or contains a `ForEach` with `reflow`, uses `BernReflowBox`: after GTK's box layout is done, it compares each child's old and new positions, and moved children slide from the old position to the new one with a spring (moving again mid-animation continues from the current offset). For `Stack` and `cell_ratio` grids see "Page-level layout" below; `reflow` in other containers such as `GtkFlowBox` grids and form rows warns at build time, and the children go straight to their new positions.
- `animate`: lengths bound to state (`padding`, `gap`, `width`, `height`, `Grid`'s `min_width`, the size of `Canvas` and `Image`, `Video`'s `corner`, `Rail`'s fractions) change along this spring. `Video`'s corner radius is clipped by `BernClip` while drawing, so a change only redraws.
- `nudge`: when the condition becomes true, the element scales up to 1.06 and springs back with `jelly`; `ScrollView(arrival: nudge)` makes the item scrolled to by setting `position` nudge once it has settled.
- `scroll_scale`, `scroll_opacity`: every time the scroll area's adjustment changes and every time the element is allocated, scale and opacity are set by the distance from the element's center to the viewport's center.

### Self-drawing and images

- `Canvas` is `BernCanvas`: a solid-color `Shape` is drawn as the renderer's own nodes; the fill is a color under a rounded clip of the same outline, and the stroke is a border extending half a line width to each side of the outline (coinciding with cairo's stroke); only `fade`, dashes, `Series` and patterns use cairo, each drawn into an image of its own, and an empty `Canvas` draws nothing. Previously it was a `GtkDrawingArea`: every draw rasterized the whole area into a cairo image on the UI thread and then uploaded it, even for an empty `Canvas` used as a spacer. Drawing elements are read in one binding and redrawn when state, size or colors (system appearance, contrast, the app's accent color and appearance) change; colors are resolved at draw time by the appearance of the part the control is in. Patterns are drawn stripe by stripe, `twill` overlays thin 45° lines, and no bitmap is cached.
- The `fill_from` image is read in the background (`GFile`, a local file or http(s)), turned upright by its EXIF orientation, scaled down to 32×32 to take the average color, and cached by URL; until it has been read, `fill` is used. `fade` is a linear gradient fading to transparent toward one side.
- `Image(source: app.x)` is read in the background and then shown, and shows nothing for `None`; when only one side is given, the other follows the image's aspect ratio.
- A picture from the network that does not come is tried again (2026-11-05, `pictures.rs`). After a failed network or a 408, 429 or 5xx answer it waits about 1, 2, 4, 8, 16 and 32 seconds, give or take a quarter, then rests until the network changes (`GNetworkMonitor`) or a window comes to the front. An address the server answered without a picture is not asked again on the same network. A view that is unmapped stops trying, and one that is mapped starts over at once. Fills from a picture go the same way. http(s) addresses are read with libsoup rather than through `GFile`: gvfs has no timeouts, does not tell the status of an answer, and may not be installed, so a `.deb` now depends on `libsoup-3.0-0` instead. A session's `timeout` of 15 seconds covers a stalled connection. Measured with libsoup 3.4.4 and 3.6.6 over TLS and HTTP/2 through a relay that stalled: three requests sharing the connection all failed with `G_IO_ERROR_TIMED_OUT`, libsoup closed the connection, and the next request in the same session had a new one, so the session is not replaced. `cargo test` runs `pictures.rs` against a server that fails on purpose. Checked in a real application on Ubuntu 24.04 with Broadway: the tries came at those waits and then rested, a healed server was not asked until the view came back, and the snapshot then showed the picture. A window coming to the front and the network changing were only exercised through the functions they call.

### Window chrome, idle and dialogs

- `idle_after`: pointer motion, key presses, scroll wheel and presses in the window's capture phase restart the timer, and when it expires `window.idle` is true. When content moves under a stationary pointer, GTK reports pointer motion at the same position; motion whose position has not changed does not count as input, otherwise the window would be woken immediately by its own layout change when the picture expands to fill it.
- `idle_area` (2026-10-24): an element with it registers as an idle area of the window when it is decorated. The window records the last position of the mouse (and touchpad, pointing stick) in the window, and records it as outside when it leaves the window; touch, stylus and emulated pointer events do not record a position. When a mapped idle area is on screen and the most recent pointer is a mouse, both starting the timer and its expiry use GTK's picking (`gtk_widget_pick`) to find the control that receives events at that position, walk up its parents to the idle area it is in, and time with that area's seconds; over no idle area, or outside the window, there is no timing. Picking follows the same rules as input, so an event-receiving control standing on top of an idle area takes the mouse away from the idle area; picking happens again at expiry, so a control bar that appeared under the stationary mouse on wake-up is not hidden right away. When an idle area is mapped, unmapped or leaves the UI, the timer restarts at the next main-loop idle. Keys, touch and stylus still follow `idle_after`. At the same time `window_landscape` is declared as not applicable: desktop windows have no orientation, on Linux phones (such as Phosh) the compositor rotates the whole screen by the sensor, and Wayland has no protocol for an app to request an orientation, so `landscape` has nothing to do and the check no longer warns.
- `immersive`: when true, `reveal-top-bars` is turned off for all header bars in the window (the window's own and those of the sidebar and the detail); and when the window is also idle, the pointer is hidden.
- `chrome: unified`: the header bar uses the flat style of `AdwToolbarView` (`flat`), with no separating shadow any more; the content does not extend under the header bar.
- `role: dialog`: set as a transient window of the main window and modal, closed by Esc; on GNOME mutter attaches it to the main window (not verified: the test environment, Broadway, has no window manager, and the dialog appears in the top-left corner).
- Window size classes: a zero-height probe at the top of the window content measures the width and, by the three breakpoints of `[layouts]`, yields `compact`, `medium`, `expanded`, `large`, which `window.compact` and the like in expressions read; another probe filling the area over the window content measures the height, and `window.short` is true when it is below `compact_below`. `Adaptive` chooses for each of the four classes; a class without a layout of its own shows the next larger declared layout, or the smaller one when there is no larger one. `Adaptive` chooses by the width its container "offers": its container `BernOffered` requests no minimum width horizontally, so the wide layout currently shown does not push the window or the probe wider (otherwise it would stay on the wide layout forever); a layout wider than the offered width is clipped until the width selects another class.
- Runtime accent color and appearance: the expressions of `WindowSet(accent:, appearance:)` are evaluated in each window; the accent color is written into a higher-priority style sheet as `@define-color accent_bg_color`, `accent_color` (slightly darker in light windows and slightly lighter in dark ones, so it stays readable on the window background) and `accent_fg_color` (black or white by luminance), rewritten when the appearance switches; the appearance is set through the color scheme of `AdwStyleManager`. libadwaita 1.5 has no interface for setting the accent color; this is the way it supports.
- Parts with `appearance: dark` / `light`: the first time one is used, libadwaita's own `base.css` and the named colors of the other appearance are read from libadwaita, each rule is scoped under `.bern-appearance-dark` (or `light`), and the named colors are replaced with that appearance's values (the accent color keeps following the window), and the result is loaded as a style sheet; controls in the part, and popovers and menus popping up from it, are therefore drawn in that appearance, and the semantic roles of canvases are resolved by it as well. It takes effect only on the part's descendants; the part's own background is determined by its content.

### Components and input for media apps

- Files: `pick` uses `GtkFileDialog` (filtered by the kind's extension table, the same judgment as for drag and drop; `folder` picks a directory), stores the selection in the field as a `file://` URL and then runs the action; the kinds and extension tables are provided along with the generated code. The filter does not include wildcard MIME types such as `video/*`: KDE's open panel (through the portal) filters by exact MIME type and matches no wildcard at all, so previously not even mp4 files showed when picking a video, and the extensions in the same filter had no effect either (2026-10-27, KDE on the Steam Deck). `ui.set_file` validates the URL (`file`, `http`, `https`, otherwise `invalid_url`) and the kind (otherwise `unsupported_file`) and then hands it to the button, menu item or `Drop` with `pick`.
- Keyboard shortcuts: one capture-phase key controller per window, taking the most recent control in mount order; `cmd` and `ctrl` both mean Control. Shortcuts without Control or Alt do not fire while editing text. A shortcut focuses the search field for `Search`, toggles `Switch` and `SplitButton`, and activates buttons, menu items and `PopoverButton`.
- `ScrollView(snap:, position:)`: when scrolling stops (unchanged for 160 ms), the nearest item is aligned to the anchor; when the scroll has moved more than 24 points from the last stop and the nearest item is behind, the next item in the direction of motion is taken, so a single scroll-wheel notch also advances. With `center`, space is left at the start and end according to the largest item; positions are computed from the item's coordinate in the content plus the content's padding, independent of the current scroll. When the field is set to another item, it scrolls there with `smooth`; on first display, once the padding takes effect, it stops directly at the field's item.
- Control targets in repeated items carry the key of each level, including through components (`card.open_swatch[2]`).

## Page-level layout, scene and control-shape capabilities (2026-10-18)

The GTK capability description added the 29 `features` that previously only SwiftUI and Web declared (`text_weights`, `text_lines`, `image_corners`, `sidebar_width`, `controlled_values`, `search_palette`, `image_template`, `adaptive_images`, `scaled_scene`, `accordion_layout`, `capsule_controls`, `modal_flow_timer`, `page_badges`, `idle_control`, `fill_buttons`, `grid_cells`, `page_search`, `form_layout`, `modal_cover`, `window_short`, `edge_grow`, `delayed_appear`, `toolbar_leading`, `axis_padding`, `icon_menus`, `icon_labels`, `row_baseline`, `sidebar_header`, `untitled_detail`), motion added `appear_delay`, `nudge_key`, `nudge_scale`, `reduce_motion`, and styles added `background`, `foreground`, `corner` for `Stack`. `window_landscape` was not declared at the time, and the check gave a warning (since 2026-10-24 it is declared as not applicable, see "Window chrome, idle and dialogs"). The check of a real media app on GTK went from 67 errors to 0 errors, and the app was built and run (see "Verification log").

### Appearance and text

- `Stack` styles are drawn on the stack itself: the background of `bern-style-<name>`, the color of text and symbolic icons (CSS `color` inherits downward), and the corner radius; with a corner radius, `overflow: hidden` clips the layers to it.
- `text { … }`: each text style also gets a class `bern-text-<style>`, and the style sheet writes the weight and size from `style!`, at application priority, above the theme's `title-1` and similar classes.
- `Text(lines:)` uses `GtkLabel`'s `lines` with a trailing ellipsis; `font_size` (bindable) and `line_height` are Pango's absolute font size and absolute line height attributes. `Label(font_size:)` also sets the icon's pixel size; `display: icon` shows only the icon, with the title as the tooltip and the accessible name.
- Text takes its single-line width first and wraps only when it does not fit: GTK's horizontal box measures a wrapping label's width for the row height (width-for-height), and with a taller element next to it the text gets squeezed into a narrow multi-line strip; `Text` is wrapped in a `BernWords` that ignores the given height when measuring width, and the same goes for marked text.
- `Image(corner:)` is clipped by `BernClip` with a (bindable, springable) radius; `rendering: template` uses `BernTemplatePicture`: the image's alpha is used as a mask filled with the foreground color (GSK's `push_mask`); `aspect` replaces the image's own aspect ratio, and when only `aspect` is given the image fills the container width with the height in proportion (the height depends on the width, the minimum height is 0, and in scroll views it is laid out at its natural height).

### Control shapes and controlled values

- `shape: capsule` is the class `bern-capsule` (9999 corner radius, likewise for the first and last buttons of grouped controls); `height` uses a size request and removes the theme's minimum height and vertical padding (class `bern-sized-control`). `IconButton(height:)` is a circular button of that diameter, `font_size` is the icon's pixel size, and `prominence: prominent` has an accent-color background. `Button(width: fill)` stretches horizontally. `ControlGroup` draws one capsule itself (an `alpha(currentColor, 0.1)` background, 40 high by default), and the buttons, popover buttons and menus in the group are all segments that likewise draw no background: a circular hit area of 30, vertically centered, with 5 on each side, a circular fill only on pointer hover and press, and no separators, consistent with the shared glass on macOS. Previously it was a libadwaita `linked` group in which each button drew the background of its own segment; an `IconButton` with motion is wrapped in a motion box that the `linked` rules do not recognize, so it became a rounded button of its own and did not join up with the popover button next to it (the screenshot and fullscreen buttons of the player screen, 2026-10-27).
- `Menu(style: icon)`: a round flat menu button showing only the icon, with the label as the tooltip and the accessible name.
- Controlled values: `Switch(checked:)`, `Picker(selected:)`, `Slider(current:)` show the value of the expression, and on change run the action's command with the argument that is identical to that expression replaced by the new value; a `Switch` or `Picker` bound to a draft and with an action writes the draft first and then runs the action. A controlled slider only moves the thumb while dragging and commits on release; keyboard and scroll wheel commit immediately. `PickerOption` gives its own value and label. `label_hidden` does not show the label and uses it only as the accessible name.

### Layout

- `padding_x`, `padding_y`: override the left and right, and the top and bottom, margins respectively on top of `padding`. `Row(align: baseline)` uses GTK's `BaselineCenter` alignment.
- The declared width and height are the requested size: a `Column` or `Row` with `width` or `height` is wrapped in `BernSized`, and `Stack` measures itself; none of them asks to be wider because of its content (such as an untruncated long title) any more.
- `Grid(row_gap:)` sets the row spacing separately. `Grid(cell_ratio:, cell_extra:)` uses `BernCellGrid`: the column count is computed from the minimum width, each row is column width ÷ `cell_ratio` + `cell_extra` high, items are placed from the top of their cell, and taller content extends into the row gap below.
- `Flow` is `BernFlow`: children each take their natural width and wrap to the next line when they do not fit; a line is as high as its tallest child, and children are vertically centered within the line; a `Spacer` (with the `bern-spacer` style class) takes no width when wrapping and, once the line is laid out, gets the remaining width of its line.
- `ScaleBox` is `BernScaleBox`: children are stacked in the declared logical size (top-left aligned), and the whole is scaled by one transform to fit and centered, with any overflow clipped, so images, text and hit areas stay aligned. `Positioned` fills the stack it is in and places its content by (springable) `x`, `y`, `width`, `height`. `Positioned`, the motion box (`BernMotion`, the wrapper used by appear, disappear and `animate`) and `Rail` themselves do not receive input (`contains` is false); only their content does (a `Rail` over the poster timeline holding only the "now" line used to block taps on the posters below): their extent runs from the container's corner all the way to the content's far corner, otherwise a layer at the bottom of the scene (such as the player's bottom control bar) would block taps on the layers above it (2026-10-27, on the Steam Deck only the bottom control bar could be tapped).
- `Positioned(bleed:)`: `BernScaleBox` computes the empty space around the canvas (in scene points) when it allocates; a layer with `bleed`, when allocating its content, looks up to the nearest `BernScaleBox` (it does not extend if another layer is in between) and extends each canvas edge it reaches to the edge of the empty space. Each of the four edges is a spring following the layer's `animate`, and which edges are reached is judged by the position the layer is heading to. When the window changes aspect ratio GTK only changes the scene's transform, and child widgets of unchanged size are not reallocated (`gtk_widget_allocate` goes through `ensure_allocate_on_children`), so as soon as the empty space changes, the box first calls `queue_allocate` on the layers with `bleed` in the scene, and the extension jumps to the new value right away.
- `Marquee`: the content, at its natural width, runs from beyond the right edge to beyond the left edge, once every `duration` seconds, with `phase` as the starting progress; when `paused` it stops where it is, and with Reduce Motion it rests at 28% of the width; the text has a 1-point black shadow; `opacity` is bindable.
- `PreviewList`: the +N marker that the items that do not fit collapse into is a capsule (`fill.strong` background, 6 on each side, at least 30 wide, `more_height` high), with only the text in the secondary color; previously it was just a line of dim text.
- `Accordion`: column widths are determined by one weight spring from 0 to 1 per column; collapsed columns have a fixed width, and the total width stays constant; each column is clipped with the `corner` radius. While staggered columns have not all arrived, the width is still distributed across the declared `count` columns, and the columns that have arrived are already in their final positions.
- `reflow` now also applies to the layers of a `Stack` and the cells of a `cell_ratio` grid (sharing `Slides`: after layout, old and new positions are compared, and items slide from the old position to the new one with a spring); `GtkFlowBox` grids and form rows still only warn.
- Scroll views: content is laid out at its natural size along the scroll direction (the viewport uses the `Natural` policy in that direction), and a horizontal scroll view takes the content's natural height.

### Page structure

- `SidebarHeader` is fixed above the sidebar list; a header with `role: title` is dropped at generation: the sidebar's header bar already shows the app name, and KDE's button layout (`icon:minimize,maximize,close`) also shows the app icon at its leading edge, so putting the icon and name in the sidebar again would duplicate them; `Sidebar(width:)` fixes the sidebar width of `AdwNavigationSplitView` in pixels; with `Detail(titled: false)` the detail header bar no longer shows the selected item's name; `SidebarItem(badge:)` shows a count at the end of the row (hidden when 0).
- Toolbar items before a `Spacer` go at the leading edge of the page's header bar (after the back button), and those after it at the trailing edge; `Text` can be placed in a toolbar.
- Tabs: in wide windows the switcher is in the page's header bar, and in compact windows (`window.compact`) it becomes an `AdwViewSwitcherBar` below the page, as in GNOME's adaptive apps; `TabAccessory` sits between the page and the bottom tab bar.
- `Form(gap:, row_height:, padding_x:, padding_y:)` and `Section(style: plain, padding_x:, padding_y:)`: the section gap is the box spacing; row height and row padding are written as one rule generated per value (for plain rows and the `box.header` of libadwaita rows), and the `Section`'s own padding takes precedence; plain sections do not take the form's row height and padding, only their own; plain sections drop the list's background, border, padding and separators, and a form that begins with one starts at the top of the page: the 24 at the top of the form is given to the first item by the style rule `.bern-form-rows > :first-child:not(.bern-plain-section)`, so it follows along when a conditional branch replaces the first item. The padding of non-libadwaita rows now comes from the rows' CSS, so that these rules can override it.
- A `Search` in a page is a `GtkSearchEntry`; `width`, `height`, `font_size` are the field's own size and font size, and the results are listed in a popover below the field (existing implementation).

### Modals, search panel and timers

- `Modal` is within the window: a `BernModal` goes into the window's overlay; it is itself a translucent backdrop that fills the window and absorbs input (0.24 black, 200 ms fade-in), with the card centered, at the declared size and at least 16 points from the window edges; without a declared height the card takes its natural height at that width (a vertical `ScrollView` inside it turns on `propagate-natural-height` and reports the height of the content it scrolls), with a 24 corner radius, a shadow and a thin border; with `cover: compact` it fills the whole window in compact windows, without corner radius or border. The element's `appear` and `disappear` act on the card. While a modal exists, the content below does not take focus; after the card leaves (its disappear transition finished), the backdrop layer is removed along with it. Measured (2026-10-25, Ubuntu 24.04 VM, Broadway): a real app's sign-in popup without a declared height is as tall as its content and grows when the status gains a line; with the window shrunk to 720 × 480, the card stops 16 points from the top and bottom, the body scrolls, and the buttons are visible.
- `Search(style: palette)`: a flat trigger button (icon and prompt); when opened, it shows the same modal card within the window (640×480 by default), with the search field and a close button on top and the results below. The results are built only while the panel is open and released when it closes. The up and down arrow keys move between `SearchItem`s whose `navigation` is true (in on-screen order), Return selects the current item, or runs the submit action when there is no current item; Esc, the close button or a click outside the card closes it; resting the pointer on an item selects it. A shortcut that activates the target opens the panel. A selected `SearchItem` closes the panel first and then runs its action (including picking a file with `pick`).
- `Timer`: while enabled and shown, runs its action every `interval` seconds (no less than 0.05 seconds); turning it off or leaving cancels the next run.
- `Window(idle_enabled:)`: when false, `window.idle` stays false and no timing happens; when it becomes true, timing starts again.

### Motion additions

- `appear_delay`: waits on top of the stagger delay; with a delay, `appear` also plays on first display.
- `nudge_key`: nudges once each time the value changes; `nudge_scale` is the nudge's scale factor (default 1.06).
- `reduce_motion`: when true, the whole app runs with Reduce Motion (equivalent to `BERN_MOTION=reduce` and to the system turning animations off).
- The `grow(edge:)` transition: grows from 0 along one axis, with that edge staying fixed and no fade. The scale of the motion layers can now specify a fixed point (`pivot`), and `scroll_origin_x` and `scroll_origin_y` now use it too.

## Value types named like framework types (2026-10-21)

The generated GTK app carries the app's value types in `bern_gtk` values and writes type names only in strings (`b::label("Layout", 0)`, `b::display(&c.engine(1), Some("Color"))`), without declaring corresponding Rust types, so the app's types never meet the GTK and libadwaita types (`Window`, `Button`, `Image`, `Orientation`, `Align`, `Widget`) (for the rule see "Language bindings" in the design document). Types named `Error`, `Text` and `Window` in the protocol module only shadow that module's glob import of the prelude; macro-generated code and the generated glue both refer to the protocol by full path (`names_protocol::names::Adapter`) and compile as usual. `tests/framework_names.rs` generates the example `examples/framework-names` and checks these forms; when GTK 4.14 and libadwaita 1.5 are installed, it type-checks the generated app with rustc. Measured (2026-10-21, Ubuntu 24.04 VM, aarch64, rustc 1.99.0): generated on the Mac and copied to the VM, `cargo check` passes (32.8 seconds, reusing the shared `bern-glue-linux` cache; the files added by this run were deleted after the check).

## Components and sessions named like framework types (2026-10-21)

The generated `ui.rs` writes components as `fn c_` plus the declared name (`fn c_empty`, `fn c_bern_player`) and describes sessions by a name string and an index (`b::SessionDef { name: "URL", … }`); the generated code imports only `b`, `V`, `rt` and `Rc`, and `bern_gtk` has no functions starting with `c_` either, so the components and sessions that SwiftUI and Compose renamed this time (`empty`, `scroll`, `bern_player`, `URL`, `Window`) do not collide on GTK, and the generator is unchanged (for the rule see "Language bindings" in the design document). The `Window` in the example changed from a protocol value type to a UI session. `tests/framework_names.rs` gained assertions on how component functions and sessions are written; this time they were not run and the app was not type-checked on the VM: not verified.

## Build and run

```sh
cargo run -p bern-cli -- build --manifest examples/showcase/Bern.toml --target linux
target/bern/linux/Showcase/showcase
```

Requires the GTK 4.14, libadwaita 1.5 and libsoup 3 development packages (Ubuntu: `libgtk-4-dev`, `libadwaita-1-dev`, `libsoup-3.0-dev`). The build outputs are in `target/bern/linux/`: `Showcase/showcase` (the UI program), `Showcase/resources/` (bundled resources, which the program finds relative to its own location), `Showcase/dev.bern.showcase.desktop`, `bin/showcase` and `bin/showcase-mcp`, the app crate `app/`, and the build manifest `build.json` (recording the minimum GTK and libadwaita versions, the media backend and presentation, and the resource names). The Rust build directory is `target/bern-glue-linux/`.

The app icon is at `Showcase/icons/dev.bern.showcase.png` (the 512-pixel Bern logo when `[app].icon` is not declared). At startup this directory is added to the icon theme's search path, and the window's default icon name is `bundle_id`; if it cannot be found, this is reported on standard error. The generated `.desktop` file points to it by absolute path. When `[app.icon].linux` is an icon theme folder, the largest PNG in it becomes this file, and all icons are renamed to `bundle_id` and placed under `Showcase/icons/hicolor/`, from where the `.deb` installs them into `/usr/share/icons/hicolor`. Under Wayland GNOME takes the dock icon from the installed `.desktop` file; after the generated file is copied to `~/.local/share/applications/` the dock shows the logo; the build does not write into the user's directories.

During development, `BERN_SNAPSHOT_DIR` makes the program render each window to `<directory>/<window>.png` after every change (including changes of `window.idle`) (nothing is drawn while a window is minimized; popovers are separate surfaces and are not included), `BERN_APPEARANCE=light|dark` overrides the system appearance, `BERN_MOTION=reduce` runs with Reduce Motion, and `BERN_MOTION_LOG` writes every transform, `reflow` offset and stagger delay with millisecond timestamps to standard error; all of them are off by default.

### Packaging

`bern package --target linux` builds in release mode and produces `<program>_<version>_<arch>.deb` (when the system has `dpkg-deb`) and `<product>-<version>-linux-<arch>.tar.gz`:

- The `.deb` installs the app, the icons and the CLI and MCP server from `bin/` to `/opt/<bundle_id>`, plus `/usr/share/applications/<bundle_id>.desktop`, icons in the `hicolor` icon theme and a `/usr/bin/<program>` launcher; it depends on `libgtk-4-1 (>= 4.14)` and `libadwaita-1-0 (>= 1.5)`, adds `libgtk-4-media-gstreamer` and `gstreamer1.0-plugins-good` when media is used, and recommends `gstreamer1.0-libav`. The maintainer is taken from `[app].publisher`.
- When `Svg` is used, the `.deb` also carries an AppArmor profile, `/etc/apparmor.d/<bundle_id>`. WebKitGTK uses bubblewrap to sandbox the web process, which needs to create a user namespace; from Ubuntu 24.04 on (`kernel.apparmor_restrict_unprivileged_userns = 1`) only programs whose AppArmor profile has `userns` can create one, and when the sandbox fails WebKitGTK aborts the whole app. The profile is the same as the ones Ubuntu provides for its bundled WebKitGTK apps (epiphany, devhelp and others): `flags=(unconfined)`, giving the program only a name and the `userns` permission without adding restrictions, and including the optional `local/<bundle_id>` for administrators to extend; the attachment path is `/opt/<bundle_id>/<program>` (`/usr/bin/<program>` is a link to it, and AppArmor matches the resolved path). The profile is listed as a conffile, so `dpkg` keeps the administrator's changes; it is kept on remove and deleted on purge. `postinst` loads it immediately with `apparmor_parser -r -T -W` only when AppArmor is enabled (`aa-enabled`), and a failed load does not affect installation; `postrm` deletes the compiled cache on purge. The profile uses AppArmor 4 syntax (`abi <abi/4.0>`, `userns`), which earlier AppArmor cannot parse (the load fails, and installation completes as usual). Apps without `Svg` carry no profile and no maintainer scripts.
- The `.tar.gz` and development builds carry no profile. To run an app that uses `Svg` on a system that restricts user namespaces, add the same profile for the unpacked UI program (needs root; quote the path when it contains spaces); `bern package` points this out:

  ```sh
  sudo tee /etc/apparmor.d/<bundle_id> >/dev/null <<EOF
  abi <abi/4.0>,
  include <tunables/global>
  profile <bundle_id> /unpacked-dir/<product>/<program> flags=(unconfined) {
    userns,
  }
  EOF
  sudo apparmor_parser -r /etc/apparmor.d/<bundle_id>
  ```

  For testing only, you can also run with `WEBKIT_DISABLE_SANDBOX_THIS_IS_DANGEROUS=1`, which turns off WebKitGTK's web process sandbox.
- Executable permissions are kept while staging; before packaging, files are normalized to 644 and programs and directories to 755, and maintainer scripts are also set to 755.
- Measured (2026-10-12, Ubuntu 24.04 ARM64): `.deb` 1.06 MB, `.tar.gz` 1.9 MB; `desktop-file-validate` passes, and `apt-get -s install` resolves all dependencies; after unpacking the `.deb`, starting it from the `/opt` location and driving it through the bundled CLI works. sudo on the VM needs a password, so it was not actually installed. Without a desktop session, GTK startup waits for a D-Bus portal timeout of about 25 seconds, and only then are the engine and the control channel ready.
- Measured (2026-10-18, same VM, AppArmor 4.0.0~beta3, WebKitGTK 2.52.3, bubblewrap 0.9.0, `examples/svg-animation`): `.deb` 1.2 MB, containing `etc/apparmor.d/dev.bern.svgdemo`, `DEBIAN/conffiles`, and `postinst` and `postrm` with permissions 755; both scripts pass `sh -n`; `apparmor_parser -Q -K` (no kernel load, no cache) parses the profile, with the result `Mode: unconfined` and `userns`; `apt-get -s install` newly installs only this one package. When the unpacked program runs without the profile, after about 26 seconds it reports `bwrap: setting up uid map: Permission denied` and `Failed to fully launch dbus-proxy` and aborts. Loading a new profile needs root, and sudo on the VM needs a password, so the `.deb` was not installed and the program was not run with this profile itself; instead the system's own `busybox` profile of the same form (`profile busybox /usr/bin/busybox flags=(unconfined) { userns, … }`) was used, starting the same program through `busybox env`: the program, WebKitNetworkProcess, both bwrap layers, xdg-dbus-proxy and WebKitWebProcess all carry the `busybox (unconfined)` label, the sandbox is set up successfully, the app does not abort, and the SVG displays correctly in Broadway. ## Keyboard shortcuts that follow state, and rebinding (2026-10-24)

Keyboard shortcuts that follow state are generated as `b::bound_shortcut(c, b::str(…), …)` and `KeyShortcutProps { bound: Some(…) }`: the window's capture-phase key controller reads the text on every key press and parses it by Bern's rules. `b::ShortcutInput` is a button; pressing it sets the window's `recorder` to it: the key controller hands key presses to it first (Control is written as `cmd`; with Shift held, the key without Shift is taken), Esc leaves it unchanged, Backspace or Delete alone clears it, and modifier keys alone keep it waiting; while it waits, shortcuts do not run. The displayed text is written like `Ctrl+Shift+K`. `MenuBar` is not generated (GNOME apps do not use a menu bar). Verification: `bern-gtk` unit tests on GTK 4 on macOS cover how keys are written, reading the text on every press, and empty text not claiming a key; generator tests (gallery) cover the generated code; not run on Linux.

## Scroll bars shown only for the mouse (2026-10-27)

`ScrollView(indicators: mouse)` generates `mouse_indicators: true`: a capture-phase `EventControllerLegacy` is added to the scrolled window and looks at the `InputSource` of the event's device on motion, press, scroll and touch begin. Mouse and trackpoint set the policy for that direction to `Automatic` (GTK's overlay scroll bars appear with the pointer), touchscreen and pen set it to `External` (scrolling still works, no scroll bars are shown), and other sources change nothing; it starts as `Automatic`. On Wayland, touchpad pointer motion is usually reported as a mouse. Verification: `bern-gtk` compiles on GTK 4 on macOS; not run on Linux.

## Status bar items (2026-10-28)

`StatusItem` has no GTK control to use; `status.rs` in `bern-gtk` provides a StatusNotifierItem (`/StatusNotifierItem`) and a `com.canonical.dbusmenu` menu (`/MenuBar`) on the session bus under the name `org.kde.StatusNotifierItem-<pid>-1`, and once it has the name and `org.kde.StatusNotifierWatcher` is present, registers with it once (a watcher that appears later, for example a restarted Plasma, gets registered with again).

- The icon is `icons/<bundle_id>.png` next to the program, scaled to 16, 22, 24, 32, 48 and 64 as ARGB32 pixels (network byte order, non-premultiplied) (`IconPixmap`); without that file, the theme's `application-x-executable` is used; `Title` and `ToolTip` follow `label`.
- Menu: the generated code's `status_menu` adds the declared items to `StatusMenu`, and the runtime adds "Open <main window title>" in front and "Quit" after, with separators only between items. The menu is built in an effect and rebuilt when the engine state it reads changes; only when the structure or text changed does it increment the revision and emit `LayoutUpdated`; `AboutToShow` builds it once more. Item IDs are depth-first ordinal numbers (the root is 0); `Event(clicked)` runs the item's action at the next idle. Check items carry `toggle-type: checkmark`, submenus carry `children-display: submenu`, and underscores in labels are doubled (dbusmenu uses them to mark mnemonics).
- `Activate` opens the main window; on Wayland, the token the status area gives through `ProvideXdgActivationToken` is first set as the window's startup ID, so that the window can take focus.
- The menu's context does not belong to a window (`Ctx::detached`) and only reads engine state; command failures are shown in the open main window. Generated code uses `Ctx::with_local` to bind `ForEach` rows and the variables of `if let` and `match`.
- The app already keeps running after its last window closes, and the status item does not change that; "Quit" calls `Application::quit`.
- With `login_item`, the menu has "Open at Login" (a check item) before "Quit": checking it writes `$XDG_CONFIG_HOME/autostart/<bundle_id>.desktop` with `glib::KeyFile` (`Type=Application`, `Name` is the app name, `Icon` is the `bundle_id`, `TryExec` is the program path, and `Exec` is the program path, quoted by the desktop file rules with `"`, `` ` ``, `$`, `\` and `%` escaped, plus `--at-login`), and unchecking deletes it; the menu is rebuilt right after the choice. The check state is read from this file each time the menu is built: it shows as checked only when `Exec` matches the current program and there is no `Hidden=true` or `X-GNOME-Autostart-enabled=false`. Uninstalling the `.deb` does not delete this file in the user's directory; `TryExec` makes the session skip it once the program is deleted.
- When the command line has `--at-login` and a status bar item is declared, `run` registers the application first, after connecting all signal handlers: if an instance is already running, the process simply ends without activating that instance; otherwise the first activation opens no window, and later activations (clicking the icon, launching again) open the main window as usual. Registering emits `startup`, so it must come after the handlers are connected; in the first measurement, registration came first, `startup` fired with nothing connected, and the engine did not start. Sandboxes such as Flatpak need to register autostart through the background portal, which is not implemented; Bern does not build Flatpak packages yet either.

Verification (2026-10-28, `bern-ubuntu` VM, Ubuntu 24.04, GTK 4.14, a debug build of the Linux version of the monitor brightness app, running on Broadway): the VM has no desktop session, so inside `dbus-run-session` a minimal StatusNotifierWatcher (Python and GDBus) stands in for the status area, and `gdbus` does the reading and writing. After closing `main#1` through the CLI, the process is still there with no window; after `Activate`, `main#2` appears; after closing it again and sending `Event(clicked)` to the first item, `main#3` appears; after sending `Event(clicked)` to "Quit", the process ends. `bern-gtk`'s clippy (all features, warnings as errors) and 108 tests pass on the VM. ## Tables, controlled text and the clipboard (2026-10-29)

`Table` is a `GtkColumnView` with `GtkMultiSelection` (`table.rs`):

- The model is a `gio::ListStore` in which each item is a "position": it holds the key and item of the row currently at this position, and the column cells read it. When items are reordered, each position switches to its new row and the cells update along with it, without rebinding; when the row count changes, positions are added or removed only at the end. Each column's `SignalListItemFactory` creates the cell on `setup`, creates a scope for this row on `bind`, and releases it on `unbind` and when the table is cleaned up.
- Each cell is a box with the `bern-boundary` class (`parent::bound_content`, expanding neither horizontally nor vertically), named after the row's key; Bern's expansion refit (`refit`) stops at the boundary and no longer walks up through the parents into ColumnView's own row widgets: before, when a cell contained a `Spacer`, the refit changed things all the way into ColumnView's internals, and on row recycling (`splice`) GTK reported `gtk_widget_get_next_sibling` and `insert_after` assertions and crashed.
- Selection: `selection-changed` writes the keys of the selected rows into the draft in row order; when the draft changes (external entry points, the row menu), the selection is set to exactly those rows, and a flag between the two directions prevents writing back.
- Sorting: each column has a `CustomSorter` that compares nothing (the row order is decided by the engine); clicking a header makes ColumnView change its sorter, and on `changed` the column's action runs; `sorted` and `descending` set the header arrow through `sort_by_column`, and setting it does not run the action.
- Row menu: secondary click (`GestureClick`), long press (`GestureLongPress`) and the `Menu` and `Shift+F10` keys find the row by the name of the cell under the pointer; if that row is not selected, only it is selected first, then a `GtkPopoverMenu` opens there. Menu items are actions in the table's own action group, each registered as a button for the external entry points.
- Primary action: ColumnView's `activate` (double-click, Enter). External entry points: role `table`; `select` takes comma-separated keys, and `value` is the selected keys.

`TextInput(current:)`: the control's model can be a value that reads state plus `change`; while the field has focus (`contains_focus`) nothing is written into it, on losing focus the state's text is written back, and every `changed` calls `change`. `paste:` (`features::pasting`) reads text with `GdkClipboard::read_text_async` on press, and only when there is text does it write it into the draft and run the action; `Button`, `IconButton`, `MenuItem` and the menu bar's `CommandItem` all go through it. `copy_text`: `host.rs` installs the platform services before starting the engine, and `copy_text` goes back to the main thread through `glib::MainContext::default().invoke` and calls `set_text` on the `GdkDisplay`'s clipboard.

Verification (2026-10-29, `bern-ubuntu` VM, Ubuntu 24.04, GTK 4.14, a debug build of a real app running on Broadway): display and selection in the server table, right-click first selecting that row and then showing the menu, menu items running, clicking a header to change the sorting, and the primary action through the external entry point; a stress script that repeatedly adds, removes and reorders rows hits no GTK assertions; every edit in the controlled input field of the subscription edit window (through `ui edit`) reaches the engine; copying a share link from the row menu and reading it back with the `paste` button gives exactly the same content. Real keyboard input on Broadway was not tested (typing was replaced by the external entry point); not looked at in KDE or GNOME desktop sessions.

## Actions that follow a value, text color and the login item switch (2026-10-29)

`Watch` (`scene.rs`) is an effect: it reads the value (tracked), and when it differs from the previous `Value`, it runs the action inside `untrack`, so the state the action reads does not become its dependency; it always runs the first time. `Text(color:)` gives the label libadwaita's text classes `accent`, `success`, `warning` and `error`, i.e. colors suited to text that change with the appearance, not fill colors. The model of `Switch(login_item: true)` is `b::login_model()`: it reads the login item state cached in `status.rs` (reading the autostart file the first time), and on a change writes or deletes `~/.config/autostart/<bundle_id>.desktop` and then reads it again; the status bar menu's "Open at Login" uses the same state, so the two follow each other.

Verification (2026-10-29, `bern-ubuntu` VM, a Linux debug build of a real app running on Broadway): sidebar page changes, table row selection and the search field reach the engine through `Watch` (after switching to a group only that group is listed, the inspector shows the selected server, and search keeps only the matching rows); latency is shown in green, and error lines in the log carry the error class; turning on "Open at Login" in the settings window writes the autostart file and the switch reads back as on, and turning it off deletes the file; `bern-gtk`'s clippy and 107 tests pass.

## Capabilities for the lyrics page, and grid width (2026-10-31)

- Blur that follows state, conditional bold, the scroll anchor ratio `anchor` and hand scrolling `browsing` are implemented, see the design document. The blur radius follows `animate`'s spring through `bind_number`; bold adds `label.bern-bold` (more specific than the text style classes); a text's `animate` also makes a bound font size follow the spring.
- When `Grid(min_width:)` is wider than the available width (for example a long list built on demand, written as one column with a very large `min_width`), each cell's minimum width used to be `min_width`, and the grid stretched the page to tens of thousands of pixels wide, pushing the content at the ends of rows and the player bar further down the same page out of the window. Now a zero-height probe above the grid measures the available width: when `min_width` fits, nothing changes; when it does not, there is one cell per row and the cells no longer require a width, filling one column as on other targets. Until it has been measured it is treated as not fitting, so the probe measures the width the grid is given, not the width the cells stretch it to.
- New Adwaita icons: `arrow.clockwise` (view-refresh), `backward.fill` / `forward.fill` (media-seek-backward / forward), `chart.bar` (network-cellular-signal-excellent, vertical bars), `checkmark.circle.fill` (emblem-ok), `heart.fill` (emote-love), `info.circle.fill` (dialog-information), `iphone` (phone), `list.bullet` (view-list-bullet), `music.note.list` (folder-music), `qrcode` (view-grid; Adwaita has no QR code), `qrcode.viewfinder` (camera-photo), `quote.bubble(.fill)` (audio-input-microphone), `rectangle.portrait.and.arrow.right` (system-log-out), `repeat`, `repeat.1`, `shuffle` (media-playlist-*), `text.bubble.fill` (chat-message-new). All checked to exist in Ubuntu 24.04's Adwaita.
- Measured (Ubuntu 24.04 VM, GTK over Broadway): the album and duration at the ends of the playlist page's rows and the player bar's controls, progress and volume are all inside the window; on the lyrics page the line being sung is bold and larger, and the lines around it blur progressively; playback progress advances (app volume set to 0).

After selecting 乙 through the CLI and then making the condition false, the selection in both windows stayed on the already unmounted 乙 (the `value` in `ui inspect` is empty), the page was blank, and no item in the switcher was highlighted; it returned neither to `fallback` nor to the first tab. Cause: the generator did not pass `Tabs`'s `fallback` to the runtime, and the runtime showed the selected item only when it was mounted; after `AdwViewStack` removes the page it is showing, it shows no page at all. The sidebar (`SplitView`) already handled `fallback`; the earlier "done" held only for the sidebar.
- Fix: the generator passes `fallback` to `b::Tabs`; when the selected value has no mounted tab, then once this update has finished mounting the replacement tabs, the selection moves to `fallback` (when it is mounted too), and otherwise to the first tab in the switcher, the same as WinUI 3 and Web. The sidebar and tabs share this choice (`settled`). When tabs are added or removed, or the runtime switches the shown page, the page the view stack shows on its own is not written back as the selection.
- Tests: bern-gtk's `a_selection_without_its_item_moves_to_the_fallback_or_the_first`; the generator test `tabs_hand_their_fallback_to_the_runtime` asserts that a `Tabs` with `fallback` passes `Some(b::get(…))` and one without it passes `None`.
- After (same probe): the window without `fallback` returns to 甲, with the 甲 page shown and 甲 highlighted in the switcher; the one with `fallback: 丁` returns to 丁, with the switcher showing "甲 丙 丁" and 丁 highlighted. Clicking 丙 in the switcher selects 丙; while 丙 is selected, 乙 appears and disappears, and the selection stays on 丙 both times.
- Seen at the same time and not yet fixed: tabs mounted later go to the end of the switcher instead of their declared position (after 乙 reappears it is "甲 丙 丁 乙"). When a `Tab` mounts, it appends its page to the end of `AdwViewStack`, and the view stack has no API for inserting at a given position. Fixed the same day, see the next entry.

2026-10-21, tabs mounted later go in their declared position (the design document's "Items of navigation containers can be dynamic too"):

- Before: see the previous entry; after 乙 reappears, the switcher is "甲 丙 丁 乙"; other targets order by declaration (WinUI 3 inserts by the item's position, Web places buttons by region, per the code).
- Fix: each `Tab` places an invisible marker where it is declared: `Tabs`'s child content is written into a GtkBox that is never shown, and the regions of conditions, `match` and `ForEach` insert the markers at their own positions as usual. When a tab mounts, and after `ForEach` reorders rows (the markers change parent containers, before the next frame and before the selection falls back), the view stack reorders its pages by marker order: `AdwViewStack` can only append, so the pages from the start that are already in declared order stay, and the pages after them are removed and added back in order, keeping titles, icons and the shown page, and meanwhile the page the view stack shows on its own is not written back as the selection (`arranged`, `TabRegistry::arrange`). Registered tabs are in the same order as the switcher, and the "first tab" for selection fallback is taken from them.
- Tests: bern-gtk's `tab_pages_follow_the_declared_order` (conditions make the second and the first tab mount later, a list moves its last row to the front and swaps two rows, and tabs with no declared position stay at the end). On the Ubuntu 24.04 VM, bern-gtk's `cargo test --all-features` (100 tests) and `cargo clippy --all-features --all-targets -- -D warnings` pass.
- Not measured: the switcher order was not looked at with the probe on Broadway, nor whether the selection and the selected page's content are kept after pages are added back; `ForEach` reordering tabs was not measured either.

## Unfinished work and known limitations

- WinUI 3 and `flutter + macos` belong to the later batches of Phase 5.
- `reflow` works in `Column`, `Row`, `Stack` and `cell_ratio` grids; a `Grid` without `cell_ratio` is a `GtkFlowBox`, and form rows are laid out by `GtkListBox`; their children cannot be given an extra offset after layout, and writing it gives a build warning.
- Apps that use `Svg` depend on WebKitGTK's sandbox, and the `.deb` ships an AppArmor profile for it (see "Packaging"). Actual installation was not measured (it needs root): `postinst` loading the profile, launching from the menu or `/usr/bin` after installation, and the situation after remove and purge are all not verified; only the package contents, the parsing of the profile and running under a profile of the same form were verified. The `.tar.gz` and development builds still need the profile added by hand, or, for testing only, running with `WEBKIT_DISABLE_SANDBOX_THIS_IS_DANGEROUS=1`.
- `Adaptive` builds as `expanded` before the first layout pass; when starting in a narrow window, the wide layout is built first and replaced by the narrow one only after layout.
- Adwaita 46 has no icons for speech bubbles, filters, sliders, sparkles or picture-in-picture, so the corresponding names use the closest icons instead: `text.bubble` → `chat-message-new-symbolic` (a bubble with a plus), `line.3.horizontal.decrease` → `format-justify-center-symbolic`, `slider.horizontal.3` → `preferences-system-symbolic`, `sparkles` → `star-new-symbolic`, `pip.enter` → `focus-windows-symbolic`. `note.text`, `paintbrush` and `paintpalette` use icons from Adwaita 46's `legacy` directory, which are still in Adwaita 51. Adwaita 47 dropped `emblem-synchronizing-symbolic` and `emblem-favorite-symbolic` (keeping only the colored `emblem-synchronizing`), so `arrow.triangle.2.circlepath` now uses `view-refresh-symbolic` and `heart` uses `emote-love-symbolic`, both of which are in 46 and 51 (2026-10-27, `cargo test --all-features` passes in full on Arch's Adwaita 51).
- `hero` pairs only within the same window; if the departing element is a video or a canvas it leaves no picture, and only the new element expands from the old position.
- Sidebar item styles have no `shadow` (the same as other targets; the check reports an error).
- `appearance` parts depend on libadwaita's own `base.css` and `defaults-*.css` (the 1.5 resource paths); Ubuntu's Yaru accent color variants are not handled separately, and the parts use libadwaita's default values.
- The search results popover does not necessarily shrink when the results become fewer (GTK popovers keep a larger size); blank space at the bottom has appeared in measurement.
- In dark parts, the accent color keeps the window mode's `accent_color`.
- Window position and moving are unavailable (a GTK 4 limitation); under Wayland the result of minimizing cannot be confirmed; virtual window presentation is not implemented (the GTK target always has native windows).
- `Menu` item icons and the `destructive` role are not rendered (GNOME menus usually have text only).
- Multi-instance windows, focus migration, packaging such as Flatpak, and icon installation are not yet implemented; the desktop file's `Exec` is an absolute path on the build machine.
- Switching tabs in the settings window builds only the selected tab.
- `idle_area` has not been built or run on Linux: hit-testing on the idle area, staying awake while over the control bar, staying awake on leaving the window, and the device sources of touchscreens and of Wayland and X11 are all not measured.
- HDR output of HDR images (GTK 4.16 and later, Wayland, color management on) was not measured: the VM used for testing has GTK 4.14 and cannot output HDR either. GTK's JPEG loader does not read gain maps, so Bern applies gain maps; GTK's color space conversion only clips and does no tone mapping, so when GTK does not output HDR, Bern converts to SDR first.
- HDR video in `Video` depends on GTK: from GTK 4.16 on, GStreamer frames carry a color space, and HDR output likewise needs color management on; not measured.
- For the other limitations shared with macOS, see the platform-independent entries in "Unfinished work and known limitations" of the [macOS SwiftUI implementation notes](macOS-SwiftUI.md).
