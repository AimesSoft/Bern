# Windows WinUI 3 implementation notes

For the current component interface, see the [component reference](../Reference/UI.md); for per-item support and the scope of recent verification, see the [platform capability table](../Reference/Platforms.md). The rest of this document keeps the implementation and acceptance records of each phase.

- Date: 2026-10-11 (the v0.29 and v0.30 capabilities were completed on 2026-10-14, see "Styles, motion, self-drawing and media app capabilities"; the page-level layout, scene and control form capabilities were completed on 2026-10-19, see the section of the same name)
- Basis: [Bern architecture design v0.30](../Design.md) (originally implemented against v0.19), [Windows and Linux adaptation](../Adaptation/WindowsLinux.md)
- Toolchain: Rust 1.99.0; Visual Studio 2022 Build Tools 17.14 (MSVC 14.44, C++20); Windows SDK 10.0.26100 (including `cppwinrt.exe`); the component packages of Windows App SDK 2.5.1 (headers and metadata only: Foundation 2.3.12, WinUI 2.3.9, InteractiveExperiences 2.1.9, plus the metadata of WebView2 1.0.3719.77)
- Verification environment: Windows 11 Pro 25H2 (build 26200, physical x64 machine), display scaling 150%

This document records the completion status of the `winui3 + windows` target from the second batch of Phase 5. The first version's host was C#/.NET: apps needed .NET 10 on the target machine and shipped about 141 MB of Windows App SDK. It has since moved to C++/WinRT: one executable contains two frontends, chosen automatically at startup, and uses only components already on the system. The showcase app's (`examples/showcase`) declaration, protocol, business core and IR are unchanged; the parser, the shared IR and the core check rules were not modified for this either.

## Host approach

**The UI is written in C++/WinRT**: no .NET is needed, the C runtime is statically linked, and the engine is linked into the same executable as a static library:

- The generated glue crate compiles the engine, the session runtime and the C interface of `bern-ffi` into `bern_app.lib` (`staticlib`, with the C runtime statically linked via `+crt-static`). The C++ runtime directly calls the same in-process interface as the SwiftUI target; callbacks copy the bytes and pass them through a message window to the UI thread, where they are handled in arrival order.
- The whole UI is built in code; no XAML pages are generated, and the XAML compiler is not involved.

**Two frontends, both compiled by default, chosen automatically at startup:**

`frontends` in `[targets.windows]` defaults to `["winui3", "xaml-islands"]`; you can also list only one of them:

```toml
[targets.windows]
platform = "windows"
frontends = ["winui3"]   # or ["xaml-islands"]; when omitted, both are compiled
```

| Condition | Both compiled | WinUI 3 only | System XAML only |
| --- | --- | --- | --- |
| The system has Windows App Runtime 2 (any 2.x: installed by another program, or built into Windows 11) | WinUI 3 (`Microsoft.UI.Xaml`), Mica background and `TitleBar`, Windows 11 look | Same as left | System XAML |
| It does not (Windows 10, or Windows 11 without 2.x) | The system's built-in XAML (`Windows.UI.Xaml`), hosted in a Win32 window through XAML Islands, Windows 10 look | A message box that can open the installer in the browser | Same as left |

- **The runtime is looked up in order.** First the bootstrapper `MddBootstrapInitialize2(0x00020000, L"", 2.0.0.0, None)` looks for any 2.x installed by another program: since 2.0, framework packages are distinguished only by major version (`Microsoft.WindowsAppRuntime.2`), and 2.x versions are compatible with one another. Apps are compiled against the latest 2.5.1 and use only interfaces that every 2.x has; the showcase app was measured page by page on 2.2 and passed. If none is found, the system's dynamic dependency API (`TryCreatePackageDependency`, `AddPackageDependency`, only on Windows 11) loads `Microsoft.WindowsAppRuntime.CBS.2`, which ships with Windows. Neither step shows a dialog or prompts an installation.
- **The runtime built into Windows.** Windows 11 25H2 ships `CBS.2` (2.2), `CBS.1.8`, `CBS.1.6` and `CBS` (1.5), all in `C:\Windows\SystemApps`, for the system's own components. Measured: ordinary programs can attach to `CBS.2` and `CBS.1.6`, but not to `CBS.1.8` or `CBS`. `CBS.2` lacks the per-language `.mui` files of the Store version, and WinUI does not find its `resources.pri` on its own: used directly, it reports `Cannot locate resource from 'ms-appx:///Microsoft.UI.Xaml/Themes/themeresources.xaml'` and exits. So when using it, the app creates a resource manager from this runtime's own `resources.pri` in `Application.ResourceManagerRequested` and hands it to WinUI.
- **WinUI 3 only.** When no runtime is found, a message in the UI language appears (titled with the app name); choosing "Yes" opens the installer of the latest runtime, `https://aka.ms/windowsappsdk/2.5/latest/windowsappruntimeinstall-<arch>.exe` (a fixed Microsoft address that redirects to the download server), in the default browser, and the app exits; once the runtime is installed, opening the app again works.
- **System XAML only.** No runtime lookup, and the bootstrapper is neither linked nor shipped; the precompiled header contains only one frontend, and the first build takes about 39 seconds.
- When WinUI 3 is compiled in, the 400 KB `Microsoft.WindowsAppRuntime.Bootstrap.dll` ships with the program.
- The two frontends share one source. The XAML part is written as `.inl` files, each included once in each of the two namespaces `bern::winui` (where `xaml` is `Microsoft::UI::Xaml`) and `bern::islands` (where `xaml` is `Windows::UI::Xaml`). Type differences are handled with `#if BERN_WINUI`, and differences in values such as resource keys with `kWinUI ? … : …`. The generated UI code `app_ui.inl` is likewise included once each in `bern_winui.cpp` and `bern_islands.cpp`. Which frontends are compiled is decided by the two macros `BERN_WITH_WINUI` and `BERN_WITH_ISLANDS`.
- Window facts, commands and close interception go through Win32 in both modes: `GetWindowRect`, `IsIconic`, `IsZoomed`, `ShowWindow`, `WM_CLOSE`, `WM_GETMINMAXINFO`. WinUI windows are taken over with a subclassed window procedure; Islands windows are Bern's own Win32 windows to begin with. `AppWindow` is used only for setting size and position under WinUI, because it knows about the frame extended into the title bar.

Generated code calls the runtime's standard components (`B::Text`, `B::SplitView`, …) in the same form as the GTK and Web targets: one function per component, expressions are C++ expressions evaluated in the context `c`, local variables live in the context, and no lambda captures anything. HDR images (PQ or HLG PNGs, JPEGs with a gain map) do not go through XAML's `Image`: WinUI 3's `Image` has no HDR ([microsoft-ui-xaml#67](https://github.com/microsoft/microsoft-ui-xaml/issues/67), [WindowsAppSDK#6291](https://github.com/microsoft/WindowsAppSDK/issues/6291)), and the system XAML documentation only says that it can decode them. After Bern recognizes an HDR image with `bern_picture_kind`, it decodes it on a background thread with `bern_picture_decode` (`bern-image`, through the `picture` feature of `bern-ffi`) into linear scRGB, uploads it on the UI thread as a Direct2D 32-bit float bitmap, and draws it into a 16-bit float swap chain in the scRGB color space inside a `SwapChainPanel`; the system compositor composites it directly, with the same code for both frontends (`ISwapChainPanelNative` has the same name but different IDs in the two SDKs' headers, so it is declared separately in the precompiled header). Light handling follows the display the window is on: DXGI reports whether it is in HDR mode and its peak luminance, and the display configuration gives the SDR brightness the user set; Direct2D's white level adjustment places the image's 1.0 at the SDR brightness, and HDR tone mapping compresses highlights to the display's peak, or to SDR white in SDR mode. JPEGs with a gain map are decoded for the display's headroom, which on an SDR display gives exactly the SDR image the author provided. As long as an HDR image is on screen, the display is checked once a second, and the image is redrawn when HDR is turned on or off, the SDR brightness changes or the window moves to another display, with gain maps decoded again for the new headroom; when the device is lost, it is recreated. Without Direct3D, or when decoding fails, it falls back to XAML's `Image`. Measured (the PC has an SDR display; the same on both frontends): the gain-map image shows as the SDR image the author provided (encoded values 166 and 241; ImageIO reads the base image as 166 and 237); the PQ image's left and right halves are 194 and 244, with no clipped highlights.

`Image` and `Stack` each have an outer `Grid`, so in columns that stretch their children they keep their own size and sit at the leading edge. Verified on the showcase app's "Images and layout" page with both frontends: the result matches macOS, and `contain` images are centered in their box; the grid has three columns; after the CLI changes volume and brightness, both progress bars update immediately.

Icons keep Bern's SF Symbols naming and map to the glyphs at the same code points in Segoe Fluent Icons (Windows 11) and Segoe MDL2 Assets (Windows 10). There is only one glyph table (`icons.rs`; the code points were confirmed by rendering and comparing the font files on the PC), which the generated catalog hands to the runtime; names missing from the table are reported as errors at check time instead of showing up blank at runtime; this check shares `bern_target_api::icon_set::check` with Web, Compose and GTK, and a test confirms that the glyph table contains every name in Bern's icon set (`icon_set::NAMES`). Four names differ on Windows 10, in `WINDOWS_10_GLYPHS`, chosen at run time by `OnWindows11`: its Segoe MDL2 Assets lacks the code points of `eye.slash`, `pip.enter` and `sparkles`, and draws `folder` as a tall page.

## Runtime structure

- **Regions and lifetimes**: content that gets rebuilt, such as conditions and lists, occupies a region of its own in the parent panel, and insertion positions are computed from the region tree. The panel holds the root region through its own `Resources`, so the region tree lives on with the panel after the build function returns. Event handlers reach the element they belong to through weak references, so no reference cycles form.
- **Reactivity**: cells, effects and scopes are the same as in the other targets; child scopes that an effect creates while running end before its next run; after a batched update, each affected effect runs only once.
- **Host**: a message-only window on the UI thread handles posted tasks (`WM_APP`) and timers (`WM_TIMER`), and works under both frontends. It also doubles as the single-instance marker: the mutex `Local\Bern.<bundle_id>`. On a second launch, the new process finds this window, hands over the foreground right, asks for the main window to be shown, and then exits.
- **App lifecycle**: the app exits after its last window closes, and the engine stops with it (WinUI calls `Application.Exit`; Islands ends the message loop); when a `StatusItem` is declared, the app stays in the notification area and is quit from its menu (see "Status bar item"). Ctrl+W closes the current window; the settings window closes with Esc and cannot be minimized or maximized.
- **External entry points**: the same local control channel as the other targets (`channels = ["ipc"]`); the CLI and the MCP server are generated from the same command catalog, also with the CRT statically linked.

## Windows

- **Close protocol**: the title bar's close button, Alt+F4 (intercepting `WM_CLOSE`), Ctrl+W, declared actions and `window.close` all evaluate the close check first. When confirmation is needed, a standard `ContentDialog` appears, styled according to the frontend. While the decision is pending, the window content cannot be operated and external entry points return `target_blocked`; when the decision is made externally, the dialog closes along with it.
- **Facts and commands**: visibility, size state, position and frame size (converted to logical pixels by the DPI of the display the window is on), focus and available actions. `minimize`, `restore`, `maximize`, `move` and `resize` reply only once the actual state satisfies the request, and return `ui_timeout` if it is not satisfied within 5 seconds. A minimized window reports the position and size it will have when restored.

## Media

The executor reports observations to the media center and never dispatches commands on its own. Each `player_id` corresponds to one player, and each loaded source gets a new Media Foundation media engine (`IMFMediaEngine`), so late events from the old engine after a source change can be recognized and dropped; volume and mute are kept on the player and carry over across source changes. Local files are converted to paths with `PathCreateFromUrlW` and handed to the engine; network addresses are handed to the engine as is. The engine's events are moved from its own thread to the UI thread before being reported, and the phase is derived following the semantics of the HTML media element (ready state, `paused`, `ended`, whether it is waiting for data).

The picture does not use `MediaPlayerElement`: WinUI 3's `MediaPlayerElement` does not show HDR ([microsoft-ui-xaml#9238](https://github.com/microsoft/microsoft-ui-xaml/issues/9238); a Microsoft engineer explained that UWP relies on CoreWindow to identify the display, and Windows App SDK apps have no CoreWindow). The engine decodes with a Direct3D 11 device with video support, enters windowless swap chain mode (`EnableWindowlessSwapchainMode`) once it has the metadata, and draws the picture into its own swap chain; `Video` shows this swap chain through the `SwapChainPanel`'s `ISwapChainPanelNative2::SetSwapChainHandle`, with the same code for both frontends (as with HDR images, the interface has the same name but different IDs in the two sets of headers, so it is declared separately in the precompiled header). This is how Microsoft's Media Foundation samples and Chromium play protected video; how HDR video is output is up to the engine and the system. The engine draws at the pixels the video occupies on screen (`UpdateVideoStream`); `SwapChainPanel` treats one swap chain pixel as one DIP, so the panel's DIP size is set to the pixel count and then scaled back down by the display scaling, which maps swap chain pixels one to one onto screen pixels. `fit` is implemented through the panel's position, its scale and clipping by the bounds: `contain` centers with margins, `cover` crops what extends past the bounds, `fill` stretches.

When the app has registered its own media core (see the [design document](../Design.md#app-provided-media-cores)), at startup it first asks `bern_media_kernel_attach` with a `SwapChainPanel`; when the core accepts, Media Foundation is not attached, and `Video` hands the panel to the core instead: what is handed over is Bern's own implementation of `ISwapChainPanelNative`, through which the core, on any thread, hands in swap chains created for composition; Bern puts the latest one into the real panel on the UI thread, and stops accepting them once the view detaches. The panel's DIP size is set to the video box's physical pixel count and then scaled back down by the display scaling; the core draws the whole video box (`fit` and margins are handled by the core), and `bern_media_surface_resize` is called when the video box size or the display scaling changes. The frame clock is a thread named "Bern media frames": it waits for the primary display's vertical blank (`IDXGIOutput::WaitForVBlank`, timing by DWM's refresh period when that is not available) and, holding a lock, calls `bern_media_surface_frame` for every attached surface, with the time given as performance-counter seconds; once a surface detaches or the app stops, no more frames arrive.

An engine has only one swap chain, so a player shows its picture in only one view at a time (`multi_view: false`): the most recently attached view shows it, and when that view detaches, the picture goes back to the previous view that is still present, consistent with Web's single view.

Measured (2026-10-12, the PC has a 2560×1440 SDR display at 150% scaling, state read back through the CLI; everything below was tested on the WinUI 3 frontend, and on the Islands frontend the HDR10 test clip and moving the preview player between pages were tested, with the same results): after the featured clip loads, `Ready 0 / 8000`; play, pause, playing again after finishing as `Ended` (which restarts from the beginning), seeking to 5000, mute and volume 0.4 all take effect; after switching to color bars, mute and volume are kept, and after switching to a damaged file, `Failed` ("The file is damaged or its format is not supported (0xC00D36C4)"). A 4:3 test clip in 16:9 bounds is correct with all three `fit` values and is laid out again after maximizing and resizing the window; the correct video size shows that the scaling correction at 150% works. The app-level preview player plays on the project detail page, and after returning to the video page, the picture appears in the video page's view. An HLS live stream served over local HTTP is `Ready` after opening and `Playing` after playback starts, `duration_ms` is empty, `media seek` returns `not_seekable`, and the picture is fine. A test clip encoded with ffmpeg as 10-bit HEVC (BT.2020, PQ, HDR10 metadata), with the left half SDR white (203 nits) and the right half 4 times that, is tone-mapped by the system in SDR mode: left and right are 237 and 252, the gradient is smooth, with no washed-out look. Output in HDR mode is not verified: the test PC has no HDR display. Window captures for development snapshots (`PrintWindow`) include the video picture.

## Styles, motion, self-drawing and media app capabilities (v0.29, v0.30)

Completed on 2026-10-14: the Windows capability description now lists styles (`Button`, `IconButton`, `SidebarItem`), motion (`appear`, `disappear`, `reflow`, `hero`, `animate`, `scroll_scale`, `scroll_opacity`, `nudge`, `stagger`), `window_chrome`, `text_marks`, `dynamic_items`, all components (no unimplemented components remain), and all 18 items in `features`. `examples/planner` and `examples/gallery` check on Windows with no errors and no warnings (tested). Both frontends use the same code; it is written separately only where the controls or resources differ, and the differences are noted below.

### Style overrides

- Each style in use generates one `B::StyleDef`: a `Look` for the base appearance and for each state (hover, pressed, focus, disabled, selected).
- A button's background, foreground and border are written as lightweight styling resources in the button's own `Resources` (`ButtonBackgroundPointerOver`, `ButtonForegroundPressed` and so on, one set each for the light and dark themes) and switched by the control template's own visual states; states the style does not cover keep the system's look and feedback. `none` makes that state the same as the normal state, and `system` keeps the system's. `corner` is `CornerRadius` and `padding` is the padding; the size classes `small`, `large` and `extra_large` have minimum heights of 24, 42 and 52 and also adjust the font size and the left and right padding.
- Scale, offset and opacity go on the "state" layer (see "Motion"), entering with the spring of the topmost animating state, and returning to the normal state uses `settle`; states come from pointer enter, leave, press, release, capture lost and focus events, and disabled comes from `IsEnabled`.
- `shadow`: Direct2D's shadow effect draws a bitmap from the button's corner radius and size (keeping only the part outside the button's shape), which is placed under the button and scales and moves together with it inside the same outer layer; shadows for different states switch by opacity. Buttons whose style draws no background, stroke or fill in any state (bare icons or text, such as playback controls floating over the picture) instead cast the shadow from their content (2026-10-25): each piece of text, icon, image and shape in them takes its own alpha mask (`GetAlphaMask`) for a Composition drop shadow, drawn on a canvas behind the button and following the content's layout, so that, as with SwiftUI's `shadow`, it is the shadow of the glyphs rather than of a box. `Stack`'s `shadow` also casts from the content inside it this way.
- Buttons with content (`Button { … }`) drop the button's own frame and background and show the content as is; `corner` clips the content with Composition rounded-rectangle geometry. When the content fills the available space, the button stretches with it.
- Sidebar items: background and foreground are written as `NavigationViewItem` lightweight styling resources (`NavigationViewItemBackgroundPointerOver`, `…Selected` and so on); with `selected: fill(…)`, the selected item fills its whole row, and the navigation view's own selection indicator is made transparent. Transforms such as scale apply to the item: `NavigationViewItem` rejects `UIElement`'s `Translation` and `Scale`, so the transforms are written on its own Composition visual. `indicator` is not listed: `NavigationView` draws its own indicator only at the leading edge, and it cannot be replaced by a shape that a style describes.
- Sidebar item transforms and the indicator: when the selection changes, `NavigationView` measures the positions of the old and new items' indicators with `TransformToVisual`, and plays the sliding animation only when their x coordinates are exactly equal (600 ms in total: in the first 200 ms the indicator stretches from the old item to the new one, cubic Bézier (0.9, 0.1, 1.0, 0.2); in the last 400 ms it contracts onto the new item, (0.1, 0.9, 0.2, 1.0); the old bar fades out during the last 400 ms, and the two bars overlap, so they look like a single bar); otherwise the two items' indicators each scale at the same time for 600 ms (linear), which looks like two separate vertical bars. The measured positions include the scale written on the items' visuals (the WinUI core's `GetLocalTransform` includes transforms the app sets on a visual), so on a click the clicked item is in the middle of its hover and press scale, and the latter path is always taken. Therefore: (1) every time the selection changes, the runtime temporarily removes the transforms from all sidebar items and writes them back after the measurement, all within the same call, so nothing shows on screen: for clicks and key presses the order is `ItemInvoked`, measurement and animation, `SelectionChanged`, so the transforms are dropped in the former event and restored in the latter (they are not dropped when the clicked item is already selected; when the selection ends up not changing there is no `SelectionChanged`, and a posted task restores them); when the runtime writes `SelectedItem` itself, it wraps the write on both sides. (2) When a sidebar item scales, its horizontal origin is the line the indicator sits on (found through `SelectionIndicator` in the template, taking the x coordinate, within the item, of the cell that contains it), so the row grows and shrinks from the leading edge, the indicator stays on the track it slides along, and the old and new bars overlap while sliding. According to the 2018 WinUI source (where the system version comes from), the navigation view of system XAML (Islands) has no x-coordinate check, and `SelectionChanged` comes before the animation; (1) has no effect there but does no harm, and (2) still makes the two bars overlap. Durations and curves are taken from `NavigationView.cpp` in microsoft-ui-xaml (`AnimateSelectionChanged`, `PlayIndicatorAnimations`, `PlayIndicatorNonSameLevelAnimations`).
- Semantic roles map to each frontend's theme resources: WinUI 3 uses `SolidBackgroundFillColorBaseBrush`, `CardBackgroundFillColorDefaultBrush`, `TextFillColorPrimaryBrush`, `AccentFillColorDefaultBrush` and so on, and system XAML uses the `SystemControl…` family; roles that system XAML lacks get one value each for light and dark. Places that need concrete colors, such as canvases, read the current colors of the theme brushes from hidden probe elements in the window, so they follow the appearance of the part they are in and the runtime accent color.

### Motion

- Springs: mass 1, stiffness (2π / T)², damping ratio ζ, the same as in the other targets; all moving springs advance together in `CompositionTarget.Rendering`, once per frame, and when the target changes they continue from the current value and velocity. When the system turns animations off ("Settings → Accessibility → Visual effects → Animation effects", `UISettings.AnimationsEnabled`), state transforms, staggering, nudges and scroll-linked effects do not run, and appearing and disappearing are only a short fade in and out.
- Transform layers: an element's movement, scale and opacity are composed from the springs of several layers (style state, appear, disappear, shared element, reflow, nudge, show, rail), with offsets added and scale and opacity multiplied, and written to `UIElement.Translation`, `Scale` (with the element's center as the origin) and `Opacity`, without changing layout. Elements that animate are wrapped in an outer `Grid`, and the transforms are written on that layer.
- Appear and disappear: elements that `if`, `match` and `ForEach` mount after the first display play `appear`; elements inside an element appear together with it. An unmounted element with `disappear` stays in the panel through an exit hook in its own `Resources` until it finishes playing and is then removed, receiving no clicks in the meantime; it is no longer in its region, so new elements are inserted at the positions they would have if it were not there.
- `stagger`: a container carries a counter while building its direct children; children with `appear` start `stagger` seconds later one after another, with the wait counted in rendered frames, waiting for their turn in the starting pose (hidden); when the container appears in an update, its children play their appearance too; `ForEach` rows count from 0 on every update.
- Shared element `hero`: when an element unmounts, its position and size in the window content (excluding Bern's own transforms) are recorded. The leaving element itself moves to its original position in an overlay (a `Canvas`) above the window content; once a new element with the same key in the same window is laid out, it expands from the old position and size with the `hero` spring, and the old element moves with the same spring and fades out. `ConnectedAnimationService` is not used: it requires preparing and starting in pairs during navigation, which does not suit elements that conditions and lists unmount and mount at any time.
- `reflow`: the panels of `Column`, `Row`, `Grid` and `ScrollView`, as well as these panels when they hold a `ForEach` with `reflow`, compare each child's old and new positions after layout, and moved children slide from the old position to the new one with a spring. `reflow` in other containers, such as forms and `Layers`, has no effect (without a warning).
- `animate`: lengths bound to state (`padding`, `gap`, `width`, `height`, `Grid`'s `min_width`, the size of `Canvas` and `Image`, `Video`'s `corner`, `Rail`'s ratio) change with this spring. `Video`'s rounded corners are a Composition rounded-rectangle geometry clip.
- `nudge`: when the condition becomes true, the element scales up to 1.06 and springs back with `jelly`; `ScrollView(arrival: nudge)` makes the item that setting `position` scrolls to give a nudge once it has settled.
- `scroll_scale`, `scroll_opacity`: Composition expression animations that read the `ScrollViewer`'s scroll property set (`GetScrollViewerManipulationPropertySet`) and compute scale and opacity from the distance between the element's center and the viewport's center, without going through the UI thread while scrolling. Element positions and the viewport size are written into the expression parameters on layout updates.

### Self-drawing and images

- `Canvas` draws with Direct2D on the UI thread into a WIC bitmap allocated for the display scaling, which is then written into a `WriteableBitmap` shown by `Image`; it redraws when the state, the size, the element's appearance or the runtime accent color changes. Same code for both frontends. `Shape`'s `fade` is a linear gradient fading to transparent toward one side, and strokes are inset by half the line width; `Series` is areas and lines; `Pattern` draws stripe by stripe, and `twill` overlays thin 45° lines (`text.primary`, opacity 0.05).
- `fill_from` images are read in the background (`file:` from disk, http(s) from the network), scaled down to 32×32 with WIC to take the average color, and cached by URL; until the image has been read, `fill` is used.
- `Text(mark:)`: takes the rectangle of each line of text from the `TextBlock`'s `TextPointer` and draws a capsule-shaped mark under the text, 74% to 98% of the line height tall, extending 0.4 character widths on each side.
- `Image(source: app.x)` is read in the background and then shown, and shows nothing when `None`; when only one side is given, the other side follows the image's aspect ratio.

### Window chrome, idle and dialogs

- `idle_after`: pointer moves, presses, wheel and key presses on the window's root element (including handled events) restart the timer, and when it runs out, `window.idle` is true. A pointer move counts only when the cursor's position on screen actually changes: when an immersive window changes its chrome, the system reports another pointer move at the same position, which would otherwise wake the window up again immediately.
- `idle_area` (2026-10-24): elements with it register as an idle area of the window when they are decorated. Mouse moves and presses on the root element record the mouse's position in the window content (`GetCurrentPoint(nullptr)`); touch and pen are not recorded; on leave, the root element also receives the leave events bubbling up from its parts, so only a leave whose position falls outside the content counts as being outside the window. When a loaded and visible idle area is on screen and the latest pointer is a mouse, both starting the timer and its expiry use `VisualTreeHelper::FindElementsInHostCoordinates` to get the topmost element at that position, walk up its parents to the idle area it is in, and time with that area's seconds; over no idle area, or outside the window, there is no timer. Hit testing follows the same rules as input, so a hit-testable control standing on top of an idle area takes the mouse away from the idle area; on expiry the hit test runs once more, so a control bar that appeared under a resting mouse on wake does not hide again immediately. When an idle area loads, unloads or leaves the UI, a retiming is posted to the UI thread. Key presses, touch and pen still follow `idle_after`. Both frontends use the same code.
- `window_landscape` (2026-10-24) is declared as not applicable: desktop windows have no orientation; on a tablet the whole screen rotates, which is the same as on iPad, where `landscape` keeps the device orientation. The check no longer warns.
- `immersive`: when true, hides the title bar and the detail header. Under WinUI 3, `TitleBar` collapses and `OverlappedPresenter.SetBorderAndTitleBar(true, false)` removes the system title bar and the caption buttons; under Islands, `WS_CAPTION` is removed from the window style (keeping the resizable border). When the window is also idle, the pointer is hidden (`ShowCursor`).
- `chrome: unified`: under WinUI 3 the content already extends into the title bar, and the title bar shows the window title next to the icon (as the Fluent windows in the design mockups do); `unified` does not change that; under Islands the system title bar is kept.
- `role: dialog`: has no top-level window of its own; it is a `ContentDialog` on the main window (or on the first ordinary window at the time it opens), with its width set from the declared size within the range a dialog allows; every close of the dialog (including Esc) goes through the close protocol. Dialog windows report the position of the window they belong to, and `minimize`, `maximize`, `move` and `resize` return `target_unavailable`.
- Window size classes: the width of the window's root element gives `compact`, `medium`, `expanded` or `large` by the three breakpoints in `[layouts]`, which `window.compact` and the like read in expressions; `Adaptive` chooses for each of the four classes separately, a class without its own layout shows the next larger declared layout, and when there is no larger one, it takes a smaller one.
- Runtime accent color and appearance: the expressions of `WindowSet(accent:, appearance:)` are evaluated in each window. Control templates take their colors from the accent brushes in the theme dictionaries (including aliases and merged dictionaries); the runtime finds these brushes (two sets, light and dark, each recording which shade of the accent color it corresponds to), changes their colors directly, and updates `SystemAccentColor` and `…Light1–3`, `…Dark1–3`, so existing controls change color immediately; the shades are approximated by mixing with white and black. Appearance is set on the `RequestedTheme` of the window's root element; WinUI 3's caption buttons follow through `AppWindowTitleBar.PreferredTheme`, and the Islands system title bar follows through DWM.
- Parts with `appearance: dark` / `light`: the part's root element sets `RequestedTheme`, and since XAML theme resources already resolve per subtree, the controls and canvases in the part and the flyouts that pop out of it (the flyout's presenter gets the same theme set separately) draw in that appearance.

### Components and input for media apps

- Files: `pick` uses `FileOpenPicker` (with extension filters by kind) or `FolderPicker` (`folder`), handed to its window through `IInitializeWithWindow`; after a selection, it stores the `file:` address in the field and then runs the action. `ui.set_file` validates the address (`file`, `http`, `https`, otherwise `invalid_url`) and the kind (otherwise `unsupported_file`) and then hands it to a button or menu item with `pick`, or to a `Drop`.
- `Drop`: the content area accepts dragged-in files (`StandardDataFormats.StorageItems`); `over` is true when the kind matches, and on drop it takes the first matching file. With `opens: true`, files on the command line and files passed in on a second launch (the second process forwards them to the first through `WM_COPYDATA`) are handed to it too; the build does not register file associations.
- `Pinch`: touch pinches come through the scale of `ManipulationDelta`; touchpad pinches arrive on Windows as the mouse wheel with Ctrl held, and scale by e^0.1 per notch. `Swipe`: press, then drag along the axis; `distance` (default 300) covers the whole range, increasing upward and to the right; it captures the pointer and runs the action on release.
- Keyboard shortcuts: each shortcut is a `KeyboardAccelerator` on the window's root element, mounted and unmounted with its control; `cmd` and `ctrl` are both Control. A `Search` shortcut focuses the search box, toggles and split buttons toggle, and buttons, menu items and popover buttons activate; shortcuts have no effect while their control is disabled, and shortcuts without Control or Alt do not fire while a text box has focus. Menu item shortcuts are shown in the menu.
- Toolbar search and results: the search box is an `AutoSuggestBox`; results are arbitrary components, so instead of its own suggestion list they are shown in a `Flyout` below the search box, which opens when the search box has focus and there are results, and closes after a result is picked.
- `PopoverButton`: the button's `Flyout`, whose content mounts when the flyout opens and unmounts after it closes; `presented` follows in both directions. `SplitButton`: a `ToggleSplitButton`, whose main part toggles and whose side part opens the same kind of flyout; that part's accessible name is `more_label`, or "More options" without it. Bubbles without a specified background color use the system's in-app acrylic (`AcrylicInAppFillColorDefaultBrush` in WinUI 3, `SystemControlAcrylicElementBrush` in system XAML), taken from the theme dictionary by the bubble's own appearance (the `appearance` of its region, or the window's), and are constrained to the window (`ShouldConstrainToRootBounds`): a flyout that extends beyond the window is a separate popup window, and in-app acrylic shows only its base color there. Previously, styled bubbles replaced the appearance-based background with a style that contained only the appearance and the text color, so bubbles in dark regions had a light background (fixed on 2026-10-26; the style now inherits from the appearance-based one). Measured (WinUI 3, and system XAML through a forced fallback): the playback settings bubble over the video is dark acrylic; WinUI 3's in-app acrylic is nearly opaque (luminosity opacity 0.96), while system XAML's shows more of the picture behind it.
- `Toast`: shows the system `InfoBar` where it is placed (informational severity, not closable, with `icon` as its icon), sliding in from below and fading out after `duration` seconds; it shows again when its content changes, and is announced as a polite live region. System XAML has no `InfoBar`; under Islands it is a bar of the same shape with a corner radius of 4.
- `Inspector`: its container becomes a `SplitView` with the pane on the right (`Inline` mode); when `presented` is true, the pane slides out and the rest of the content makes room.
- `ScrollView(snap:, position:)`: when scrolling stops (`ViewChanged` is no longer intermediate), it takes the nearest item and aligns it to the anchor with an animation; with `center`, space is left at the start and end according to the largest item, and positions are computed from the item's coordinates in the content plus the content's padding. The item it settles on is written back to `position`; when the field is set to another item, it scrolls there with an animation; after the first layout, it rests directly on the field's item.
- Control targets in repeated items carry the key of every level, including through components (e.g. `card.open[3]`).

## Page-level layout, scene and control form capabilities (2026-10-19)

The capability description adds the 29 `features` that previously only SwiftUI, Web and GTK declared (`text_weights`, `text_lines`, `image_corners`, `sidebar_width`, `controlled_values`, `search_palette`, `image_template`, `adaptive_images`, `scaled_scene`, `accordion_layout`, `capsule_controls`, `modal_flow_timer`, `page_badges`, `idle_control`, `fill_buttons`, `grid_cells`, `page_search`, `form_layout`, `modal_cover`, `window_short`, `edge_grow`, `delayed_appear`, `toolbar_leading`, `axis_padding`, `icon_menus`, `icon_labels`, `row_baseline`, `sidebar_header`, `untitled_detail`), motion adds `appear_delay`, `nudge_key`, `nudge_scale` and `reduce_motion`, and styles add `Stack`'s `background`, `foreground` and `corner`. `window_landscape` was not declared at the time, and the check gave a warning (since 2026-10-24 it is declared as not applicable, see "Window chrome, idle and dialogs"). Both frontends use the same code (the new code is in `bern_ui_scene.inl` and the existing parts), except that in system XAML the sidebar count becomes a number after the name (its navigation items have no `InfoBadge`). The icon table adds 33 names (e.g. `house` → Home, `calendar` → Calendar, `text.bubble` → Message, `server.rack` → MediaStorageTower, `gobackward.10` → SkipBack10, `goforward.10` → FastForward, `sparkles` → SearchSparkle), with the code points taken from the official Segoe Fluent Icons list.

### Appearance and text

- `Stack` styles: the stack is wrapped in a `ContentControl` whose `Foreground` is inherited down to text and `FontIcon`; the background is drawn on the stack's `Grid` (roles follow the theme through `ThemeResource` styles, fixed colors follow the element's theme), and `corner` is `Grid.CornerRadius` plus a Composition rounded clip, which clips every layer to the rounded corners. `Stack(enabled: false)` uses the same wrapper's `IsEnabled`: all controls inside it are disabled and receive no input.
- `text { … }`: the catalog carries the weight and size of each text style, and `Text` and `Label` set `FontWeight` and `FontSize` on top of the system text styles. `Text(lines:)` is `MaxLines` plus a trailing ellipsis; `font_size` (bindable) and `line_height` (`LineHeight` and `BlockLineHeight`). `Label(font_size:)` is also the icon's font size; `display: icon` shows only the icon, and the title serves as the tooltip and the accessible name.
- `Image(corner:)` is a bindable Composition rounded clip that follows the `animate` spring; `rendering: template` uses `BitmapIcon` (`ShowAsMonochrome`, colored by the foreground color where it sits); `aspect` replaces the image's own aspect ratio, and when only `aspect` is given, a panel sets the height from the container width and the ratio.

### Control shapes and controlled values

- Fluent 2 has no capsule-shaped buttons (in the Fluent column of the design mockup, primary and secondary buttons alike are `Button`s with a corner radius of 4), so `shape: capsule` keeps the corner radius of the control's own style and takes only `height`: it sets the control's height and removes the minimum height and the top and bottom padding (the left and right padding is kept once the control has entered the visual tree and its style has taken effect); a capsule button with content clips the content to the button's corner radius. `IconButton` looks like a Fluent app bar button: no background, which appears only when the pointer moves over it, the system corner radius, 10 on each side of the icon (`height` or the style's `size` gives the side length of a square); `prominence: prominent` makes it an accent-color button, round when it has a side length (the play button in the mockup); `font_size` is the icon's font size. Icon menus likewise have no background. `Button(width: fill)` fills the width. `ControlGroup` places buttons side by side like a command bar (default height 40); the buttons have no background, and the group itself draws no backing either (Fluent expresses grouping by position).
- `Menu(style: icon)` is an icon-only button plus a `MenuFlyout`; with `height` it is a round standard button, otherwise it has no background. A capsule-shaped drop-down `Picker` is a `DropDownButton` with `ToggleMenuFlyoutItem`s.
- Controlled values: `Switch(checked:)`, `Picker(selected:)` and `Slider(current:)` show the value of the expression; on a change they run the action's command with the argument that is identical to that expression replaced by the new value (integer arguments are rounded). A controlled slider moves only itself while dragged and runs the command on release; keyboard changes run it immediately. `PickerOption` gives its own value and label. `label_hidden` does not show the label and uses it only as the accessibility name.

### Layout and page structure

- `padding_x` and `padding_y` override the left/right and the top/bottom padding respectively on top of `padding`. `Row(align: baseline)`: the children are first laid out top-aligned, then each is moved down onto one common baseline by the `BaselineOffset` of its first text block (converted into the child's coordinates via `TransformToVisual`); the extra height is counted in the next measure pass.
- `Row` and `Column` (`FlexPanel`): what fills shares the free room equally, but a stack that fills only through a `Spacer` inside it starts from its own length beside a `Spacer` of the same panel, and shares only what is left, as the general rule says. With too little room the `Spacer`s take nothing and the stacks shrink in proportion. Previously such a stack counted as one more filling item: `Row { Spacer  Column { …  Row { Spacer  …  Spacer } }  Spacer }` in a 380-wide modal left the column a third of its row, 100 wide, so a fixed-width card and a row of labels were cut off (changed 2026-11-05). What fills for itself, such as a text input or a scroll view, still shares equally.
- `Grid(row_gap:)` sets the row spacing separately; with `Grid(cell_ratio:, cell_extra:)` each row is column width ÷ `cell_ratio` + `cell_extra` high, each cell is laid out from the top of its slot, and taller content extends into the row gap below. `Flow` is a wrapping panel (`FlowPanel`): items are vertically centered within their line, and a `Spacer` (role `bern-spacer`) takes no width when lines are broken and, once laid out, gets the remaining width of its line.
- `ScaleBox`: the children are stacked within the declared logical size, and the whole is fitted to the space it gets with one `CompositeTransform` (scale plus a centering translation); what extends beyond is clipped; images, text and hit areas stay aligned. `Positioned` fills the stack it is in, and its content is placed and centered by the (springable) `x`, `y`, `width` and `height`. `Positioned(bleed:)`: the context of a `ScaleBox` carries its scene margins (`Ctx::scene`; content inside a layer no longer carries them), and during arrange the margins around the canvas (in scene points) are computed from the size it gets; a layer with `bleed`, when measuring and arranging its content, extends every canvas edge it reaches to the outer edge of the margin; each of the four edges is a spring that follows the layer's `animate`, and which edges it reaches is judged by the position the layer is heading to. When the box changes shape, the scene's own size stays the same, and XAML does not re-arrange children of the same size, so when the margins change the box calls `InvalidateMeasure` on the registered bleeding layers, and the extension jumps to the new value at once. `Marquee`: the content, at its natural width, runs every frame (`CompositionTarget.Rendering`) from beyond the right edge to beyond the left edge; it stops when `paused` and stands still at 28% of the width under Reduce Motion; the text in it gets a 1-point black shadow from Composition's `DropShadow` (masked by the text's own `GetAlphaMask`).
- `Accordion`: each column has a weight spring from 0 to 1, the column widths are distributed by weight with the total width unchanged, and each column is clipped to the `corner` radius (the clip is set to the column's size on every arrange).
- Page header: toolbar items before the `Spacer` go at the leading edge after the back button, those after it at the trailing edge; `Text` can be placed in the toolbar. `SidebarHeader` is `NavigationView.PaneHeader`, and is not shown with `role: title` (the title bars of both frontends already show the window title next to the app icon); `Sidebar(width:)` is `OpenPaneLength`; when omitted the pane starts at the system default of 320, and its edge can be dragged to anywhere from 180 to 480 (see "Sidebar toggle and width" below); with `Detail(titled: false)` the page header does not show the name of the selected destination; `SidebarItem(badge:)` is an `InfoBadge` in WinUI 3 (hidden when 0).
- Sidebar toggle and width: in WinUI 3 the button that collapses the pane is the title bar `TitleBar`'s own pane toggle (`IsPaneToggleButtonVisible` and `PaneToggleRequested`), to the left of the app icon; it opens and closes the pane in every display mode, and `NavigationView`'s own button is hidden; when a window has several split views, the one shown last owns it, and hands it back and hides the button when unloaded. The Islands system title bar cannot hold a button, so `NavigationView`'s own button at the top of the pane is used (the Windows 10 look). In expanded mode, collapsing shrinks the pane to a 48-wide icon strip, and in narrow windows the toggle opens the pane as an overlay; both are `NavigationView`'s own behavior. While the pane is closed, `PaneHeader` and `PaneFooter` are hidden (they are laid out at the width of the whole pane and would be cut off in the icon strip), and they are restored when it opens. `NavigationView` has no draggable divider, and there is no system splitter control either: when no width is declared, the `SplitView` is wrapped in a `Grid`, and an 8-wide bar with a transparent background, hidden from screen readers, is placed at the pane's edge; WinUI 3 sets the system left-right resize cursor via `IUIElementProtected::ProtectedCursor`, and Islands uses Win32's `SetCursor` when the pointer enters and moves; on press the bar captures the pointer and changes `OpenPaneLength` by the horizontal position in the view (mirrored with the view in right-to-left layouts), rounded and clamped to 180–480. The bar is shown only in expanded mode while the pane is open, and moves with `OpenPaneLength`.
- `Form(gap:, row_height:, padding_x:, padding_y:)` and `Section(style: plain, padding_x:, padding_y:)`: the spacing between sections, and the minimum height and padding of card rows (the `Section`'s own take precedence); rows added later are set the same way; the rows of a plain section sit directly on the page (no card) and use only its own padding, not the form's; a form that begins with one starts from the top of the page: the panel of a plain section is named `bern-plain-section`, and the form looks at its first item (through wrapper layers) when its content has been built and when the content's size changes, so a heading given by a slot, a component or a condition counts too. A `Search` in a page sets the search box itself with `width`, `height` and `font_size`; without `width` it fills its column like a text box and takes the remaining width in a row, as on SwiftUI (previously it kept its own width, and a search box in a dialog was only a little over a hundred points wide; changed 2026-11-01).

### Modals, search panel and timers

- `Modal` is the system `ContentDialog` (the modal panel in the Fluent column of the mockup): the system's scrim, corner radius and enter and exit animations, with content at the declared size (at least 16 from the window edges); without a height, the content panel is first measured once with unlimited height (filling children such as `ScrollView` take their content height, `Spacer` is 0); if that does not exceed the window minus 32, that height is used, otherwise it is measured again at the window minus 32; there is no title or button area; items in the content that fill take the card's width, and the rest stand in the middle of the card, as in SwiftUI's card (previously everything sat at the leading edge, and popups with fixed-width content such as a QR code left a gap on the right; changed 2026-11-01); with `cover: compact` it fills the window in compact windows. It stays shown as long as the element is mounted, and Esc does not close it. It is shown only after the window's XAML root is ready, and follows the window's appearance. The element's `appear` and `disappear` are replaced by the dialog's own enter and exit transitions. A window can have only one `ContentDialog` at a time. Measured (2026-10-25, Windows 11 PC): in a real app, a sign-in popup and an add-task popup that declare no height are as tall as their content; with the window shrunk to 720 × 480 the card stops 16 points from the top and from the bottom, the body scrolls and the buttons are visible.
- `Search(style: palette)`: in place it is the system `AutoSuggestBox` (`prompt` is the placeholder text; 240 wide in a toolbar); tapping it, clicking the magnifier, typing in it or the keyboard shortcut opens the panel. The text box inside the box marks taps as handled, so taps are subscribed with `AddHandler(TappedEvent, …, true)` (a plain subscription used to receive nothing, and clicking did not open the panel; fixed 2026-10-20); the magnifier button raises `QuerySubmitted`, which also opens the panel. The panel grows out of the search box (section 10.8 of the mockup, "the search box expands in place", T17): a layer covers the window content and the page dims (black at 20% in light, 32% in dark); the panel moves from the search box's rectangle and corner radius (4) on the `hero` spring to the center of the page-header column that holds the search box, 26 below the search box, `width` wide (at least 16 from the window edges), with corner radius 8; its height is that of the input row plus the results, at most `height` (defaults 640 and 480), and when the results change the height follows the `bouncy` spring; the content fades in once the panel has grown about a third of the way; on close the content hides first and the panel shrinks back into the search box on the `snappy` spring; the search box is hidden while the panel is open. The panel uses the flyout material (`AcrylicInAppFillColorDefaultBrush`, a `SurfaceStrokeColorFlyoutBrush` border, a `ThemeShadow` cast onto the scrim; Islands uses `SystemControlTransient…` brushes and square corners). The top row, 56 high, holds the magnifier, a system `TextBox` (the text already typed carries over) and an `esc` button; below a divider are the results (padding 6), which are built only while the panel is open and released when it closes. With `Window(idle_enabled:)` false, `window.idle` stays false and no timing runs; when it becomes true, timing starts again. `window.short` means the window height is below the compact breakpoint.

### Motion additions

- `appear_delay` waits on top of the stagger delay, and with a delay `appear` also plays on first display; `nudge_key` shakes the element once each time its value changes, and `nudge_scale` is the scale factor of the shake (default 1.06); when `reduce_motion` is true the whole app runs as under Reduce Motion, the same as when the system turns animations off.
- The `grow(edge:)` transition: stretches from 0 along one axis, with that edge staying fixed and no fade in or out. The motion layer's scale can carry a fixed point, with a translation added to compensate for the scale.

### Stutter when switching (2026-10-20)

In release builds, when switching a list's filter (one column of poster rows collapses, another expands), switching pages in the settings window, and in other places that mount many elements at once with animation, the animation stalls at its start, sometimes for half a second.

- Cause one: the resource images and `file:` images of `Image` read their files synchronously on the UI thread (`ResourceBytes`, `FileBytes`). When the file is already in the system cache this is fast (see the measurements below), but when Defender is scanning freshly unpacked files or the disk is busy, one image takes tens of milliseconds: under load, bern-pc measured stalls of 0.4–1 seconds when switching, during which the UI thread itself used only 40–80 ms of CPU; the rest was spent waiting for files.
- Cause two: animations need a layout every frame (the accordion changes column widths every frame), and after a layout every element subscribed to `LayoutUpdated` receives that event (it is not tied to an element; a layout anywhere triggers it), so they all run every frame. A sampler (it pauses the UI thread and unwinds the call stack; compiled in only for diagnosis) showed where the UI thread was busy while switching the list: about 30% of the samples were in the XAML framework's own code, followed by `Canvas` redraws at about 5% and WinUI `TitleBar` updating the non-client area at about 7%.
- Images are now read in the background: the file read goes to the thread pool (`resume_background`), and once it is done the work returns to the UI thread to decode and display; if the element's scope has already been released, nothing is shown. Recently read image bytes are kept in memory by key (resource name or file path), up to 64 MB with least-recently-used eviction; a single image over 16 MB is not kept; on a hit the image is shown on the spot, so the same image mounted again does not first blank and then appear. An image's size was only known after XAML's asynchronous decode anyway, so reading in the background adds no layout jumps. `Image(source: app.x)` was already read in the background.
- Images with fixed sizes are also decoded in the background: XAML's `BitmapImage` decodes the whole image with WIC on the UI thread (the sampler saw the UI thread spending most of its time in `windowscodecs`); a real app's home page shows some twenty 88×132 posters at once, whose originals average over 300 KB and the large ones 3 MB, and on entering the home page the UI thread stalled continuously for 0.2–0.6 seconds, producing only 66 frames in ten seconds. Images whose given sides are all numbers and that do not fly (no `hero`), whether from resources or files, are now decoded on the thread pool with `BitmapDecoder`: at twice the display size multiplied by the window scale, scaled by `BitmapTransform` with the Fant filter (the JPEG decoder decodes directly at that ratio without first decoding the whole image); images smaller than that are decoded whole; they are decoded into a premultiplied BGRA `SoftwareBitmap` and put into a `SoftwareBitmapSource` back on the UI thread. After the change, entering the same home page: 456 frames in 2.6 seconds with an average interval of 5.5 ms, stalling only for about 90 ms in the frame that builds the page (41 ms of which is applying the engine state and building elements). All other images still go to `BitmapImage`.
- A `Canvas` with no content does not draw: every time a canvas appears or changes size it creates a new WIC bitmap and Direct2D render target and then copies into a `WriteableBitmap`; canvases that only take up space (spacing, the filling background in a button) did the same, and when column widths changed every frame they redrew every frame. Now no bitmap is created when the draw list is empty, and an existing one is released. The Web canvas likewise: an empty canvas no longer reallocates its bitmap on every resize. GTK (GTK's own drawing pass), Compose and SwiftUI (system canvases) have no intermediate bitmap and were not changed (not measured).
- The title bar inset fix compares first: `FitTitleBarInsets` hangs off the title bar's `LayoutUpdated` and used to query `AppWindow`'s title bar insets on every layout; now it remembers the two column widths and the scale it last set, returns immediately when neither the column widths nor the scale have changed, and queries only when the title bar itself has changed the column widths or the scale has changed.
- Style dictionaries are parsed only once: `Restyle` caches the lightweight `ResourceDictionary` it gives elements by XAML text, and elements with the same look merge the same dictionary; previously each element parsed its own. If merging the shared dictionary fails, it falls back to parsing its own copy.
- Transform layers are written once per frame: all springs of a frame are advanced first, then each element's layers write the combined result once; previously each of a layer's five springs, and each layer of an element, wrote `Translation`, `Scale` and `Opacity` separately. Values that have not changed are not written.
- WinUI's `TitleBar`, when an icon is set, subscribes to the icon's `LayoutUpdated` and unconditionally calls `InputNonClientPointerSource.SetRegionRects(Icon, …)` every time, which in turn calls `SetWindowRgn` and `SetWindowPos` (a comment in microsoft-ui-xaml's `TitleBar.cpp` says this is a workaround added for another problem: the title bar clears the non-passthrough regions after every interaction). Estimated from samples, this costs about 0.15 ms per layout and only raises CPU use without causing stalls; it was not worked around, and the title bar still uses the system icon and system menu.
- `BERN_FRAME_LOG`: when set to a non-empty value, writes to standard error, for each spring animation, the frame count, how late the first frame came, the frame intervals, the frames over 25 ms, the time spent advancing springs, the CPU cycles used by the UI thread itself (`QueryThreadCycleTime`) and the busiest frame among them, and also UI-thread stalls of more than 50 ms without a frame: the cycle count during the stall, the time spent running posted work (applying the engine state and building elements), and how many style dictionaries were parsed. Other programs were running on bern-pc at the same time, so wall-clock times varied widely; cycle counts are steadier.
- Tried and not adopted: setting `DecodePixelWidth` on `BitmapImage` (XAML already decodes at the display size, and setting it explicitly measured slower; decoding still happens on the UI thread, so images with fixed sizes later switched to decoding in the background on their own, see above); handing the transform layers to the compositor's `SpringVector3Animation` / `SpringScalarAnimation` to play (each element's visual has to be handed over when the layer is created, which cannot be combined with properties such as `UIElement.Translation`; measured: after switching, the expanded rows stayed transparent, so it was not adopted).
- Measured (Windows 11 physical machine, i5-13490F, 150%, release, the same sequence each time: open the list page, switch the filter 7 times, open the settings window, switch pages 8 times; the two versions alternated, 3 rounds each, median taken; cycles counted at 2.5 GHz, about 0.4 ns per cycle):
  - With the files in the system cache and the machine idle, changing only the image reading made no difference: in both, the first frame of a filter switch came after 31–33 ms, and neither had stalls over 50 ms. The change targets cold starts and antivirus scans.
  - After adding the empty-canvas skip and the inset comparison: UI-thread cycles per frame of the filter-switch animation 6.19 → 5.47 million (−12%); switching pages in settings 3.53 → 2.70 per frame (−24%), the frame that builds the new page 91 → 68 (−25%), first frame 27 → 22 ms. The frame that builds the new column when switching the filter is still about 82 million cycles (about 33 ms), with the time spent mostly on XAML element creation and layout.

### Text formats (`text_formats`)

- String tables in the catalog: translated text with parameters keeps Bern's format source text; text without parameters has `{{` and `}}` restored to braces; month and weekday names (`bern.date.*`) are written along with the table, in English when the language has none.
- `bern::Text::Fmt(key, {{"name", arg}, …})` parses the current language's text at runtime and then formats it. `bern::Text::Arg` is text, a number (the value and Bern's notation) or a date; the generator passes `DateArg` for `CalendarDate`, its label for an enum, and `ArgOf` for everything else (integers and decimals keep their numeric values). Plural branches look first for `=N`, then for the current language's category (Chinese, Japanese, Korean, Vietnamese, Thai, Indonesian and Malay have only `other`; in the other languages 1 is `one`), and finally for `other`; `#` writes the number; dates take fields, or month and weekday names, by runs of `y`, `M`, `d` and `E`; in durations the largest field written absorbs the larger units. Text bindings read the language cell and are written again when the language changes.
- Enum labels show variant fields: the catalog's `VariantDef` carries the fields the label shows (placeholder name and field index), and `Text::Display` fills them in as arguments according to the field type (enum fields use their own labels and can nest; a `CalendarDate` is a date). A `Text::Label` with only a variant and no value (option lists) writes these fields as empty.

### Fixes along the way

- When rows and columns distribute free space, an element given a height (width) no longer fills in that direction, even if it contains filling content: previously a `Stack` with a given height and a `Canvas` spread inside it split the remaining height evenly with another filling element in the same column.
- When `height` removed the top and bottom padding, it used to read the padding before the control entered the visual tree (the style had not taken effect yet, so it read 0) and cleared the left and right padding along with it, squeezing a button with text to as wide as its height; now it reads after `Loaded` and keeps the left and right padding.
- The order of `ScrollView`'s designated initializers did not match the declaration order of `ScrollProps` (MSVC reported C7560 when `open_at` and `indicators: hidden` appeared together).
- Controls and layout fixed against the design mockup (Fluent 2 desktop):
  - In the mockup the accent fill is the brand color itself in both light and dark, with white text (near-black text on a bright accent color); previously light used one step darker and dark mixed in two steps of white (which looked pinkish in dark areas). `AccentFillColor*` now all take the brand color, and `TextOnAccentFillColor*` takes white or near-black by luminance.
  - Menus and flyouts opened from dark areas (such as the player): with only `RequestedTheme` set, the text turned white while the background stayed the light color of the window's theme, which was hard to read; now the style also includes the system's own `MenuFlyoutPresenterBackground`, `FlyoutPresenterBackground` and border brushes from that theme's dictionary.
  - `ToggleSwitch` no longer shows "On/Off" beside it, matching the mockup. The navigation pane shows no collapse button when expanded (the narrow modes keep it).
  - The segmented control (`SelectorBar`) sits at the leading edge at its own width instead of being centered in the given width. Split buttons show an icon and a title (only the icon in a toolbar).
  - Content that appears later in a conditional branch and wants to fill (such as the `ScrollView` of each onboarding step) makes the already placed outer columns, stacks and containers fill along with it; previously the outer stretch was decided only once, on insertion, so the onboarding page's bottom bar hung in the middle.
  - A horizontal `Divider` fills the width (previously it was set to center in a stack and had zero width); `Slider` fills the width it is given (previously it shrank to 80 in `Positioned`); `Rail` takes only the size of the stack it is in and no longer makes the stack fill horizontally (previously the thumbnail stack split the remaining width evenly with a `Spacer`, and the title beside it was misaligned).
  - A `ScrollView` with only `position` and no `snap` aligns to the start, the same as on other targets; previously it centered, leaving half a viewport before and after the content, which added about 140 of blank space above the poster wall.
  - A `Canvas` without a size is the backing of the other layers in a stack: it takes their size and does not make the stack fill (the same as `Rail`; a stack with only the backing in it still fills). The canvas itself reports no desired size (the bitmap is shown in the XAML `Canvas` at the size of the outer frame), since otherwise the size it last drew would hold the stack open. Previously the background of the selected item in the optional-feature preview was stretched into a large block.
  - Text gives way when a row is too narrow: text, and rows and columns that contain text, narrow proportionally (wrapping or truncating), while controls and elements given a width keep their size, consistent with other targets; previously a longer description in a settings card pushed the switch out of the card.

  - A `Label`'s icon scales with the text's font size (1.15 times the font size), with a gap to the text of 0.6 times the font size (4 to 12); previously the icon was fixed at 16.
  - The semantic color `control.border` is Fluent's control stroke `ControlStrokeColorDefault` (the mockup's `rgba(0,0,0,.0578)`); previously it was the dark stroke of an unchecked checkbox.
  - Buttons at the toolbar's leading edge (the back side) have no background, matching the window's own back button; `play.fill` and `pause.fill` use the solid PlaySolid and PauseBold.
  - The element tree written by `BERN_DUMP_TREE` includes each element's position in the window, explicit height, and text with its font, font size and weight, for locating layout problems against the mockup; also the element's own clip, and both values when the space layout gives it is smaller than the size it wants.
  - In a button with content, content that does not fill the height is centered vertically in the button, the same as in text buttons; previously the content stuck to the top (in the 32-high "Resume" button the icon, the text and the keycap sat about 5.5 higher than centered). The clip for the style's corner radius computes the button's shape from the content's actual position in the button.

System XAML uses `SystemControlBackgroundListMediumBrush`.

## Build and run

```powershell
cargo run -p bern-cli -- build --manifest examples/showcase/Bern.toml --target windows
target\bern\windows\Showcase\showcase.exe
```

Building needs Rust and Visual Studio's "Desktop development with C++" (MSVC and the Windows SDK); .NET is not needed:

- **Build script**: finds Visual Studio with `vswhere` and loads `vcvarsall`.
- **Windows App SDK packages**: looked up first in the NuGet cache; when not found there, fetched from nuget.org into `target/bern-winrt/packages/` with Windows' built-in `curl` and `tar`.
- **C++/WinRT headers**: generated with the Windows SDK's `cppwinrt.exe` and cached per SDK and WinUI version in `target/bern-winrt/` (about 110 MB, generated only once).
- **Precompiled header**: the C++/WinRT headers and the runtime take up the vast majority of the compile (the WinUI 3 frontend alone takes about 46 seconds to compile, about 23 of them parsing headers), yet they have nothing to do with the app. `bern_pch.h` puts both into one precompiled header, one per configuration, in `app/obj/debug/` or `app/obj/release/` (about 2.4 GB). It is regenerated only when the runtime templates, the compile options, the MSVC version, the SDK or the paths change: the script writes the runtime and options fingerprint computed by Bern, `VCToolsVersion`, the SDK version and each path into `pch.key`, and the next build reuses the header directly when they match. The other five translation units are compiled in parallel with `/MP` every time, and the engine library is built incrementally by cargo.
- **Build times** (i5-13490F, 16 threads):

  | Case | Before | Now |
  | --- | --- | --- |
  | First debug build (generates the precompiled header) | about 60 s | about 82 s |
  | New project: unchanged, UI changed, engine changed | about 60 s | 5–6 s |
  | Showcase app: rebuild | about 60 s | about 9 s |
  | First release build / rebuild | about 90 s | about 95 s / 5 s |

Outputs are in `target/bern/windows/`: `Showcase/` (`showcase.exe`, `Microsoft.WindowsAppRuntime.Bootstrap.dll` and `resources/`), `bin/showcase.exe` and `bin/showcase-mcp.exe`, and the build manifest `build.json` (recording the frontends, the package versions and the minimum Windows version).

The app icon `app.ico` (a round version of the Bern logo when `[app].icon` is not declared, with one PNG each from 16 to 256 pixels) is compiled into the executable as icon resource 1, which File Explorer shows. At runtime it is set as each window's large and small icon according to the DPI of the monitor the window is on (taskbar, Alt+Tab, the Islands system title bar), and WinUI 3's `TitleBar` additionally shows the image in it closest to the title bar's size via `ImageIconSource`. `[app.icon].windows` can give an `.ico` file, which is compiled in as is; the bitmap entries in it (those that are not PNG) are wrapped by the title bar into a single-image `.ico` and then decoded.

**Development aids** (all off by default):

- `BERN_SNAPSHOT_DIR`: writes two kinds of snapshots once the UI has been still for 700 ms, and at most once every 5 seconds while it keeps changing (such as the time during playback); rendering the UI occupies the UI thread, and PNG encoding happens on a background thread (2026-10-26: previously it captured every 700 ms and encoded on the UI thread, so during playback the UI was left with about one frame per second). `<window>.png` is a render of the XAML content, with open dialogs and menus saved separately as `-popup<n>.png`; `<window>-window.png` captures the app's own window with `PrintWindow`, including the title bar, Mica and the video picture.
- `BERN_APPEARANCE=light|dark`: overrides the system appearance.
- `BERN_FORCE_ISLANDS`: tries the fallback frontend on a machine that has the runtime installed.
- `BERN_APP_RUNTIME=installed|inbox|none`: uses only a runtime installed by other programs, only the one built into Windows, or acts as if there were neither (when only WinUI 3 is compiled, the message box appears).
- WinUI's unhandled errors and failures to load control styles are written to standard error, and the process then ends as usual.
- `BERN_DUMP_TREE`: writes the element tree and sizes to standard error.
- `BERN_SNAPSHOT_BURST` (together with `BERN_SNAPSHOT_DIR`): after each change, additionally captures the on-screen window every 40 ms for 800 ms, saved as `<window>-burst<n>-<frame>.png`, for inspecting motion frame by frame.
- Debug builds write the call stack (functions and line numbers) to standard error from the PDB on an unhandled exception. The PDB stays in `app/obj/<config>/` and does not go into the app directory.

### Packaging

`bern package --target windows` builds in release and produces `<product>-<version>-windows-<arch>-setup.exe` and a `.zip` with the same name:

- The app directory and the CLI and MCP server in `bin\` are first copied into a staging directory; when `BERN_WINDOWS_CERTIFICATE` is set, `signtool` signs these programs and then the installer (a certificate store thumbprint or a `.pfx`, with an RFC 3161 timestamp). The certificate and password are read only from environment variables and are not written into the generated scripts.
- The installer is generated by Bern (`templates/installer/`), using the same MSVC. `pack.cpp` runs after signing and compresses the staged files together with Windows' Compression API (LZMS, 64 MB blocks) into one resource of `setup.cpp`; installing unpacks it with the same API, so the installer carries no decompressor. It installs per user into `%LOCALAPPDATA%\Programs\<product>` without administrator rights; it creates a Start menu shortcut and registers an uninstall entry in "Apps & features". `/S` installs silently. The manifest declares `asInvoker`; otherwise Windows would treat a program with setup in its name as an installer that needs elevation.
- The installer has one window, drawn with Direct2D: the app's icon, name and version, and one real button, which keeps the keyboard and screen readers working. There is no title bar; the window moves from anywhere but its controls. While working, the button gives way to a thin progress bar, and closing is refused. The button reads Install, Update (with the versions in the line above it) or Reinstall by the version in "Apps & features", then Open; a failure shows its reason in that line, with Try Again. The window follows the system's light or dark mode, and its texts the system UI language (English, Simplified Chinese, Traditional Chinese, Japanese). The version installed stays until the new files are unpacked.
- `uninstall.exe` in the install directory is a copy of the installer; it first copies itself to a temporary directory and runs from there, so that it can delete the whole directory; `/S` uninstalls silently. Uninstalling also deletes the `Run` value registered by the status bar item's "Open at Login" and Task Manager's record under `StartupApproved`. While the app or its tools are running (judged by process image path), both install and uninstall refuse to proceed and delete no files; `uninstall.exe` is deleted last, so uninstalling can be run again after a failure midway.
- Measured (2026-11-05, Windows 11 x64, 150% scaling, a release app of 35.3 MB in 8 files): installer 7.78 MB (35.5 MB before compression), `.zip` 11.8 MB, unpacking 0.4 s, installing 2.4 s with the bar; the installed files were identical to the staged ones. Install, Update, Reinstall, a refusal while the app runs followed by Try Again, Enter, Esc, `/S` and uninstalling were all run on a small app; the light and dark windows were checked by eye. It has not yet been built or run on Arm64.
- Measured (2026-10-12, new project): installer 5.08 MB, `.zip` 1.94 MB; after a silent install the files, shortcut and uninstall entry were correct, and the app launched from the install location and was driven through `bin\my-app.exe`; uninstalling and installing over it while it ran were both refused, and after it was closed, uninstalling removed the directory, shortcut and uninstall entry; the Chinese confirmation box displayed correctly; Defender reported nothing. When unsigned, SmartScreen shows a warning.

## State-driven keyboard shortcuts and rebinding (2026-10-24)

Keyboard shortcuts that follow state use `BoundAccelerator`: a reactive effect reads the text, normalizes it and registers a `KeyboardAccelerator`; when the text changes, it removes the old one before registering the new one; a control's shortcut is an overload of `B::Shortcut(c, [](Ctx const&){…}, id, action)`, and a menu item's key hint updates with the text (`boundShortcut`). `B::ShortcutInput` is a button that, once pressed, takes the next key press in its `PreviewKeyDown` (modifiers are read with `GetKeyState`, and Control is written as `cmd`); Esc leaves the value unchanged, Backspace or Delete on its own clears it, and it stops waiting when it loses focus; while it waits, no accelerator runs. The displayed text is written in the form `Ctrl+Shift+K`, with the Space key named in the UI language. `MenuBar` is not generated. Verification: generator tests (gallery) cover the generated code; the C++ was not compiled, and neither frontend was run on Windows.

## Status bar item (2026-10-28)

`StatusItem` is the app's icon in the notification area; both frontends share the same Win32 code (`StatusArea` in `bern_ui_windows.inl`):

- At startup a hidden top-level window (class name `BernStatusArea`) is created to receive the icon's messages, and the icon is added with `Shell_NotifyIcon` (`NOTIFYICON_VERSION_4`); the icon is the app icon in resource 1, taken at the small-icon size for the system scale; the tooltip text follows `label` (an effect that does a `NIM_MODIFY` when the text changes). When `TaskbarCreated` arrives after File Explorer restarts, the icon is added again; it is deleted when the app ends.
- A click (`NIN_SELECT`, or `NIN_KEYSELECT` from the keyboard) opens the main window; a right click (`WM_CONTEXTMENU`) opens the system popup menu at the icon (`TrackPopupMenuEx`, `TPM_RETURNCMD`). The menu is built when it opens, by the generated code's `StatusMenu` from the state at that moment: first "Open <main window title>", then the declared items (`if`, `match` and `ForEach` are generated as C++ conditions and loops; each item records the context it is in, which carries `ForEach`'s row variable), and finally "Quit"; separators appear only between two items. The chosen item runs after the menu closes. Before opening, the hidden window is made the foreground window, and after closing a `WM_NULL` is posted; only then does the menu close when the user clicks elsewhere.
- When the system is in dark mode the menu is dark too: through uxtheme's functions at ordinals 135 and 136 (`SetPreferredAppMode(AllowDark)`, `FlushMenuThemes`), which is what Windows' own programs do and how other programs call them too; when the two functions cannot be found, the menu stays light.
- With a status bar item the app does not quit after the last window closes: Bern itself does not end the app, and under WinUI `DispatcherShutdownMode` also has to be set to `OnExplicitShutdown`, otherwise WinUI ends by itself when the last XAML window closes (which is how it quit in the first measurement). "Quit" calls `Application.Exit` (Islands ends the message loop) and does not go through the windows' close checks.
- The menu's context does not belong to a window and only reads engine state; command failures are shown in the main window if it is open. External entry points do not list the menu items.
- With `login_item`, the menu has "Open at Login" (`StatusArea::Login`) before "Quit": checking it writes a value named after `bundle_id` under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` whose content is the quoted program path plus `--at-login`, and unchecking it deletes that value; both cases delete the record of the same name under `Explorer\StartupApproved\Run`. The checked state is read from the registry each time the menu opens: it shows as checked only when the value equals the current program's command (case-insensitive) and Task Manager has not recorded it as disabled (the first byte of the `StartupApproved` record is odd).
- When `Claim` sees `--at-login` on the command line it records `Host::atLogin`: if an instance is already running, this launch just ends without sending an activation message; `OpenInitial` opens no window when there is a status bar item, and the app is only in the notification area.

## Tables, controlled text and the clipboard (2026-10-29)

The Windows App SDK has no table control (DataGrid is in the Community Toolkit), so `B::Table` uses the system `ListView` for the rows, shared by both frontends:

- The whole is a two-row `Grid`: a header row on top, and a `ListView` below (`SelectionMode::Extended`, which handles multiple selection with Ctrl and Shift). Column widths are given as `ColumnDefinition`s: those with `width` in pixels, the others sharing `Star`; the header and every row's cells use the same set of definitions, with 12 between columns. The header aligns with the actual position of the cells in the rows: on a cell's `SizeChanged`, `TransformToVisual` measures its left and right offsets within the table and sets them as the header's `Margin`, so there is no need to guess the padding of `ListViewItem`.
- Header: a column with an action is a button that draws no background (`MakeSubtle`), the title plus a 10-point `chevron.up` / `chevron.down` glyph, shown when `sorted` is true, with `descending` choosing the direction; a column without an action is just text.
- Rows: one `ListViewItem` per item (`HorizontalContentAlignment::Stretch`), whose content is a `Grid` with that set of column definitions, each cell a horizontal Bern row panel. Rows are kept by key (the same approach as `B::Each`): when the items change, only rows that no longer exist are removed, the items in `Items()` are moved into the new order, and a row whose values changed updates only its cells.
- Selection: `SelectionChanged` collects the keys of the `IsSelected` rows in row order and writes them into the draft; when the draft changes (external entry points, the row menu), `IsSelected` is set row by row. A flag sits between the two directions, so selection changes the list makes itself because rows were added or removed are not written back to the draft.
- Row menu: `ContextRequested` (right click, the Menu key, Shift+F10) walks the visual tree from `OriginalSource` to the `ListViewItem` it is in; if that row is not selected, the draft is first set to just that row, then a `MenuFlyout` is shown with `ShowAt` at the pointer (on the row when opened from the keyboard). The menu items are built by `MenuEntries`, shared with `B::Menu`, and each is registered as a button for the external entry points.
- Primary action: `DoubleTapped` on a row, and Enter while a row has focus. External entry points: role `table`; `activate` runs the primary action, `select` takes comma-separated keys (returning a failure when a key does not exist), and `value` is the selected keys.

`TextInput(current:)` generates `current` and `change` (the same `model()` as a controlled `Slider`), and no `submit`. `Editable` gains a function that reads the model and a "keep" check: a controlled field does not write into the control while its `FocusState` is not `Unfocused`; on `LostFocus` it writes the engine's text back; `TextChanged` calls `change` every time. The `edit` of the external entry points goes through the same `change`.

`paste:` is in `RunOf`: on press, `PasteText` reads `Clipboard::GetContent()`; when there is no `StandardDataFormats::Text` or the text is empty it does nothing, otherwise after `co_await GetTextAsync()` it writes the text into the draft and then runs the action; if the window closes while it waits, the action no longer runs. `Button`, `IconButton`, buttons with content and `MenuItem` all have a `paste` field (in the designated initializers right after `files`). Windows has no menu bar, so the `paste` of `CommandItem` has nowhere to be used; the status bar item's menu does not read or write the draft.

`copy_text`: `Start` calls `bern_platform_install(nullptr, OnPlatformRequest)` before `bern_app_start`; when the engine makes a request from any thread, `OnPlatformRequest` copies the text and returns to the UI thread through `Post`, then calls `DataPackage::SetText` and `Clipboard::SetContent`, followed by `Clipboard::Flush` (so the text remains after the app exits). Other operations return 1, which reports `platform_unavailable` as before the install.

Verification: generator tests (the gallery's table page) cover `B::Table`, columns, the row menu, controlled `TextInput` and `paste`; the gallery was compiled with MSVC on a physical Windows 11 machine (both the WinUI 3 and Islands frontends; the first compile was missing `<set>`, which has been added to `bern_base.h`), and all backend tests passed on that machine; the Windows build of a real app succeeded. Content that arrives later still makes the outer container span through `Refill`, as before.
- Tests: the generator test `a_column_without_align_is_a_leading_one` asserts these rules and the generated code and compiles the generated program with MSVC on Windows; the default-column assertion in `content_in_a_window_starts_at_its_top_leading_corner` changed to `Left`. On the PC `cargo test -p bern-backend-winui3 -- --test-threads=1` passes (16 generator tests).
- After the change (same probe): title 31–372, the short button's center line at 203 (the title's center line at 202); small `Stack` 31–139; dividers, inputs, sliders, progress bars, grids, rows containing a `Spacer`, `Stack`s with a backing layer, `Button(width: fill)` and canvases with no width written all span the whole column; a divider and an input arriving later in a card make the card span; switches, checkboxes, pickers and long text are only as wide as their content, as on macOS, with long text wrapping at the column width.
- Still not consistent: after content that arrived later leaves, the outer container does not shrink back (after the divider in a card disappears, the first card still spans 31–448; on macOS, tvOS and GTK it shrinks back to the width of the text). Cause: `Parent::Add` and `Refill` only change roles and alignment toward "fill", and the `bern-layers-w` of a `Stack` and roles mirrored from containers are not withdrawn; this was already so before the change.

## Unfinished work and known limitations

- After filling content that arrived later leaves, the outer container does not shrink back: when a condition or query adds horizontally (or vertically) filling content to a column or `Stack`, the outer container spans along with it, and after the content leaves the outer container keeps spanning (`Parent::Add` and `Refill` only change roles and alignment toward "fill"; the `bern-layers-w/-h` of a `Stack`, roles mirrored from containers, and children's `Stretch` are not withdrawn). On macOS, tvOS and GTK the outer container shrinks back to its own size (measured 2026-10-21; see the same-day entry in the verification log).
- When the value bound to `Picker(style: menu)` is the first case of the enum, the combo box does not show the selected item (it is blank); macOS, tvOS and GTK show that case's label (seen in a probe on 2026-10-21, cause not investigated).
- **Using the runtime that ships with Windows is not a usage Microsoft documents publicly.** Microsoft's deployment guide only says that unpackaged apps deploy the runtime themselves; `CBS.2` is a copy Windows uses for its own components, that third-party programs can use it is a measured result, and future Windows updates may change its name, contents or availability. That is why a 2.x installed by other programs always takes precedence. Which Windows 11 versions ship `CBS.2` has also only been confirmed on 25H2 (26200.9457).
- When only WinUI 3 is compiled, the message box's "Yes" was only verified to open the installer's URL; no actual download and installation took place in testing.
- Apps compile against 2.5.1 and accept runtimes from 2.0 up: measured only on 2.2 and 2.5.1; there were no machines with 2.0 or 2.1.
- No MSIX packaging is provided. New unsigned programs may be misjudged by the heuristic rules of security software; formal distribution needs signing.
- The fallback frontend has no `SelectorBar`, `InfoBar` or `TitleBar`; they are replaced by a button group, a self-drawn error bar and the system title bar respectively.
- HDR images were measured only on an SDR display: the test PC has no HDR display, and brightness in HDR mode is not verified.
- HDR video was measured only on an SDR display: in HDR mode the media engine and the system output HDR; the test PC has no HDR display, so this is not verified.
- A player shows its picture only in the most recently attached view at any one time; earlier views show only the frame.
- Page tools are placed in the page header, without using `CommandBar`; the items of `Menu` do not present the `destructive` role.
- The light and dark steps of the brand color are approximated by mixing with white and black.
- `chrome: unified` does not change the title bar under WinUI 3 (the title shows as usual); under Islands it is still the system title bar.
- `indicator` on the selected sidebar item is not supported: `NavigationView` draws only its own indicator at the leading edge; sidebar item styles also have no `shadow` (the same as other targets; the check reports an error).
- `reflow` only takes effect in the panels of `Column`, `Row`, `Grid` and `ScrollView`; written in other containers it has no effect, and the build gives no warning.
- System XAML navigation items have no `InfoBadge`; the sidebar count is a number after the name.
- `Row(align: baseline)` aligns by the first text block; children without text stay top-aligned. When a baseline changes, it takes one more layout pass for the extra height to be accounted for.
- `Window(landscape:)` does not apply (desktop windows have no orientation), and a tablet does not turn to landscape because of it; the system's `SetDisplayAutoRotationPreferences` only restricts auto-rotation of the whole screen and was not adopted.
- `idle_area` has only been compiled (2026-10-24, both frontends of the generation test compiled with MSVC on bern-pc), not run: resting over the idle area, and staying awake when the pointer moves onto the control bar or out of the window, are none of them measured.
- `shape: capsule` is not drawn as a capsule on Windows and keeps the Fluent control's own corner radius (as the design mockup has it); only the fixed-size accent-color `IconButton` is circular.
- Animated SVG is a child HWND above the window: it does not follow the opacity of its ancestors or clipping other than scrolling, it covers XAML layers such as flyout menus, and during pop animations it follows only position and size.
- When an enum label with only variants and no values (such as an option list) is written out, the field the label displays is empty.
- Shared elements are paired only within the same window and are implemented with Bern's own overlay, without using `ConnectedAnimationService`.
- Search results are shown in a `Flyout` below the search box, not in `AutoSuggestBox`'s own suggestion list (the results are arbitrary components).
- The runtime accent color is implemented by modifying the accent color brushes in the theme dictionary, with each step approximated by mixing with white and black, not the palette the system computes from the accent color.
- Dialog windows are `ContentDialog`; only one can be shown on a window at a time, and they cannot be moved, resized or minimized.
- `Drop(opens: true)` does not register file associations: only files handed over through the command line and on a second launch arrive.
- Touchpad pinch relies on the system converting it to the wheel with Ctrl (the default behavior of precision touchpads).
- For the other limitations shared with macOS, see the platform-independent items under "Unfinished work and known limitations" in the [macOS SwiftUI implementation notes](macOS-SwiftUI.md).
